# 灵活的任务和 git 工作流

用户只和主管对话。主管能看懂项目、能和用户连续讨论需求，按场景决定怎么做事、怎么提交，拿不准就问用户。不再有写死的流水线和默认值。决策见 `docs/decisions/0022-flexible-not-preset.md`。

## 现状

- 代码任务验收通过后自动 commit、push、`gh pr create`（`task/advance.go` 的 `review` → `PurposeDeliver` → `node/deliver.go`），冲突时自动 rebase 最多 2 次；交付后清理 worktree。
- 新任务的起点按“指定 → 远端默认分支 → 当前分支 → main → master”挑，基于 `origin/<分支>`（`workspace.startPoint`）。
- 任务类型由有没有项目推断（`task.Create`），类型决定工作位置、是否验收、只派到开发机还是只派到服务器（`task.route`）。
- 代码和一般任务必须经过 reviewer 模型验收，没配验收模型就自动通过；不通过自动返工，最多 3 次。
- `workPrompt` 里写死“不要 push、不要创建 PR、不要切换分支，sous 会自己开 PR”。
- `project_create` 默认 wokspace（`layout` 默认 `wokspace`，主管提示词和环境说明里也这么写）。
- 合并后自动部署靠每 5 分钟用 `gh pr view` 查 sous 开出的 PR（`task.CheckMerges`）。
- 主管看不到项目文件；讨论需求只能派一次性任务。

## 需求

- R1 **不预设**：起点分支、合并目标、推送的分支、项目结构，代码里都没有默认值；工具参数必填，由主管按场景填写，拿不准就问用户。
- R2 **连续讨论**：用户在主对话或项目对话里和主管讨论一个项目的需求，主管能读项目文件、能连续多轮地向项目顾问追问；隔几天回来还能接着聊。顾问的回答原样显示，主管不转述。
- R3 **讨论和派活由主管判断**：问题和想法不建任务；明确且范围清楚的指令才建；拿不准当讨论；讨论收敛时主管提议拆任务，用户确认后派发。用户说“先别做”主管就退回讨论。
- R4 **任务属性**：工作位置（worktree / 就地 / 临时目录）、机器、验收方式由主管按场景选。就地执行在开发机上也可以；没有 git 的目录也能做任务，并能看 diff、撤销。
- R5 **验收可选**：不验收、reviewer 模型看 diff、审查岗位的 agent 实际验证、交给用户；不通过时返工或问用户。返工有硬上限。
- R6 **任务不自动交付**：任务结束在“完成，改动在分支上（或就地）”。提交、合并、推送、开 PR、撤回都是用户说了才做（或者用户明确要求的自动化）。每次 git 操作都用一句话报告做了什么。
- R7 **习惯**：用户的说法第一次有歧义时主管问一次，记住答案，以后按它理解；主管不会自作主张把操作自动化，最多问一次。
- R8 **安全边界不变**：权限模式、底线规则、硬信号、服务器的严格策略、审批上限照旧；顾问会话只读由 Node 执行，Hub 不能放宽；不对受保护分支 force push；只能撤回没推送的提交和合并。
- R9 **部署触发**：项目的部署分支（显式配置）有了新提交就可以自动部署，不论改动来自用户合并的 PR 还是 sous 的推送。

## 不做

- 执行隔离（仍在第二期，0010）。
- 多人项目的评审流程、PR 评论处理。
- 顾问会话跨机器迁移：一个项目的顾问会话固定在一台开发机上，那台离线时主管换一台新开会话。
