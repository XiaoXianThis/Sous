# 0015 页面上的项目终端，以及配套的安全收紧

- Status: Accepted
- Date: 2026-11-04

## Context

用户想在项目里直接敲命令（看日志、跑一下测试、手动修环境），不想每次都派 agent，也不想另开 SSH。项目可能在好几台机器上，所以开终端时要能选机器，还要能同时开几个。

终端等于把机器的 shell 交给页面：不经过权限策略（0005、0010），谁拿到会话 Cookie 谁就能在机器上执行命令。0012 的远程管理只跑写死的命令，终端是第一个“请求里带命令”的能力，必须单独设防。

顺带做了一次全面的安全检查，发现几处可被利用的问题：配对码可被暴力猜中、设备令牌能收到所有终端输出、远程编辑 node.json 能绕过“服务器不能远程改回开发机”和底线规则、页面没有 CSP 和防嵌入、Passkey 不要求用户验证、Hub 可以被配置成在公网明文监听。

## Decision

- 终端是一种作业（`kind: shell`），复用 0012 的伪终端、输出流和 `job.*` 接口；Node 在项目目录（工作空间里的 git 仓库）里启动本机的 shell。页面在项目弹窗里多一个“终端”标签：多个终端是多个标签，“+”选这个项目所在的机器。
- 防线：
  - 打开终端要求 15 分钟内用 Passkey 验证过（401 `reauth`，页面再验证一次）；再次验证只刷新当前会话，不换会话。
  - 终端属于打开它的登录会话（`owner`，从会话令牌推导的不透明 id）。别的会话（另一台设备、被盗的 Cookie 在别处使用）看不到、也用不了它。
  - 目录只能是工作空间里的 git 仓库；node.json 的 `remote_shell: false` 关掉它，这个开关和 `remote_admin` 一样只能本地改。
  - 输出只是临时事件，不进事件日志；打开终端这件事进日志，作为审计记录。设备令牌的事件流不再收到任何作业输出。
  - 一台机器最多 8 个终端，开着超过 24 小时自动结束。
- 其他收紧：配对码连续 5 次填错就作废全部；`/device/ws` 只推送对话相关的事件；远程编辑 node.json 只能收紧安全设置（服务器角色、底线规则、终端开关保持本地的值）；页面文件接口只服务 git 仓库；所有回答加 CSP、`frame-ancestors 'none'`、HSTS 等响应头，内联脚本移到文件里；Passkey 要求用户验证；请求体最大 4 MB；`listen` 不是回环地址时必须配 TLS（`tls_cert` / `tls_key`）或显式写 `insecure_listen: true`。

## Alternatives

- 不做终端，让用户 SSH：多台机器、手机上都不方便，而且 SSH 要另外开端口和管理密钥，攻击面更大。
- 终端命令也过权限策略：用户自己敲的命令再让用户审批没有意义，策略的正则也拦不住交互式 shell。
- 每次按键都要求近期登录：安全但没法用；改成“打开要近期登录 + 终端绑定会话”，被盗的 Cookie 既开不了新终端，也碰不到已有的。
- Hub 和 Node 之间再做一层端到端加密：Hub 本来就要读写这些数据（它是大脑，0002），端到端加密挡不住被攻破的 Hub；传输已经是 TLS（`wss`，非本机必须 https），重点放在认证和授权上。

## Consequences

- 在页面上能直接用每台机器的 shell，手机上有 Esc、Tab、Ctrl+C、方向键。
- 换设备要各开各的终端；Hub 重启不影响终端（归属记在 Node 上）。
- 被攻破的 Hub 仍然能控制机器（派 Run、远程管理、开终端），这是 0002 架构的前提；不信任 Hub 的机器应设 `remote_admin: false`。
- 更新包没有签名（0008）仍是供应链上的薄弱点，留作后续。
