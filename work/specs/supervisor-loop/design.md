# 设计：主管的闭环

拍板（2026-11-07）：D1 A、D2 A、D3 A、D4 B（不做硬规则，条条大道通罗马）、D5 A、D6 提示不拦、D7 A、D8 用户在设置页定。

实现时和下文不同的地方（以决策 [0025](../../../docs/decisions/0025-supervisor-loop.md) 为准）：

- P1：没有按任务链计深度，只用“没有用户参与的连续自动回合 ≤ 8”，它已经挡住了互相触发的循环。触发挂在任务引擎的每条汇报上（`post`），不在状态转换里逐个加。
- P2：Hub 从总结里解析“## 结果”，没有新增 `run.result` 字段；Node 的总结改为保留结尾。`report_result` 的内容在结束时补进总结。
- P3：`ask_supervisor` 不暂停 Run，而是让工具调用等着回答（暂停会取消 agent 当前这一轮）。
- P4.3：不加 `deploy_root`，复用服务器的工作空间（`workspaces`）。
- P4.4：Hub 认出 peer（机器名、主机名、`hello.addrs`、连接来源地址），只在审批说明后加提示。

目标：主管从“只在用户说话时醒来、只能写任务单”的调度员，变成能接着推进、看得到结果、把事派到对的机器上的经理。不改 0002（Hub 不动手）、不放宽 Node 的硬信号和服务器规则（0014、0023）。

基于 2026-11-07 工作区里的代码（含未提交的 0024 改动）。

## 现状和根因

| # | 现象 | 代码里的原因 |
|---|---|---|
| F1 | 任务做完，主管不接着做下一步（测完不部署、做完不验） | 完成报告是 `message.assistant`（`task/advance.go` 的 `post`），主管只被 `message.user` 和 `trigger.fired` 叫醒（`supervisor/supervisor.go` `Start`）。只有 no_action、操作被拒、改到同一文件会立刻跟进；受阻和失败要等 4 小时，Run 执行 2 小时（`trigger/trigger.go`） |
| F2 | 主管拿到的结果很浅 | 汇报是 agent 的总结截到 800 字（`doneReport`），没有“验证了什么、还剩什么、有什么疑问”这样的结构 |
| F3 | 子 agent 不能问，也不能报进度 | ACP 会话的 `mcpServers` 固定是空的（`acp/client.go`）；agent 拿不准时只能猜，或者结束一轮被判 no_action |
| F4 | “部署到服务器”变成从 Mac 用 ssh 过去 | **运维任务对服务器只是“优先”，不是“只能”**：`router.Route` 的 `Prefer` 在候选里没有服务器时退回开发机。项目没在服务器上登记目录、也没配 `deploy` 时，候选只有 Mac，ops 任务就派到了 Mac。Mac 上的 agent 只能 ssh（`ssh` 是硬信号“远程登录”，会交给用户审批，所以没有绕过安全规则，但流程是错的） |
| F5 | 主管没法把项目放到服务器上 | `project_clone` 只能 clone 到开发机（服务器跳过，`task/workbench.go`）；`project_put` 的 deploy 要求目录已经存在。“服务器已连接、项目还不在上面”这种情况，主管没有路可走 |
| F6 | 返工和重试丢上下文 | 只有从顾问交接的第一个 Run 会 `ResumeSession`（`task/engine.go`），返工、重试、换方向都开新会话，只带 detail 和恢复说明 |
| F7 | 等机器的原因不告诉主管 | 选不到机器时任务进入 `queued`，原因是“等待机器：…没有登记这个项目的目录”。这种原因是永久的，不会因为机器上线就解决，而主管不会被叫醒 |

做得好的、不用改的：每个对话一个 worker 串行，事件日志只有一个写入者，effects 幂等；`run_message` 断线重连时会重发（`nodehub/conn.go`），追加指令在一轮结束时取走（`node/run.go`）。竞态不是主要问题，**问题在于结果不回流、执行的位置不对。**

---

## P1 结果回流：任务状态变化叫醒主管（解决 F1、F7）

Engine 在这些时候，往任务的来源对话追加一条 `trigger.fired`（kind `task`）：

- 任务完成（`finish`），附上 P2 的结构化结果；
- 受阻或失败（任何原因，不再等 4 小时）；
- 需要用户验收；
- 进入 `queued`，且原因不会随机器上线自己消失（没有目录、agent 未登录或已停用、项目已删除）。

主管照常判断：有下一步就做（派发依赖的任务、部署、验收），需要用户决定就 `notify`，什么都不用做就 `stay_silent`（不发言）。

**防止自己跟自己转圈**
- 合并窗口：同一个对话 20 秒内的多条任务事件合成一次触发。
- 预算：同一个对话里，没有用户插话时，连续自动回合最多 N 次（建议 8 次），超过就停下，并 `notify` 用户一次。
- 主管在自动回合里新建的任务算作链条的一部分：任务带上 `chain` 计数，深度超过 5 交给用户。

**成本**：每个任务结束多一次主管调用。系统提示和工具定义有缓存（0020），一次大约是一段环境说明加一条触发消息的输入。

> **D1 叫醒的范围**
> - A（推荐）：上面四种都叫醒，靠合并窗口和预算控制。
> - B：只在任务带了 `then`（创建时写“做完以后打算干什么”）或者失败时才叫醒；其余的只发报告。更省，但又回到主管得预先想好的老路。
> - C：只叫醒失败、受阻和永久排队；完成仍然只发报告。

## P2 结构化结果（解决 F2）

工作 Run 的提示末尾，要求 agent 用固定的小节收尾：

```
## 结果
- 做了：…
- 改动：…（文件或命令）
- 验证：…（跑了什么、结果如何；没验证就写“没有验证”）
- 没做完 / 风险：…
- 需要决定：…（没有就写“无”）
```

Node 结束 Run 时解析这一节，存进 `run.result`（新字段，JSON）。解析失败时退回现在的总结。

- 报告消息和 P1 的触发都使用结构化结果：“需要决定”不为空时，主管必须处理。
- 新增主管工具 `task_result(task, part)`：读完整的总结、diff 的统计和某个文件的 diff、Run 日志的最后 N 行。800 字只用在消息里，主管想细看时可以自己去读。

> **D2 结果的来源**
> - A（推荐）：提示词约定加解析，零依赖，所有 agent 都能用。
> - B：等 P3 的 MCP 工具 `sous_report(...)` 来交结果，更可靠，但依赖 agent 支持 MCP。可以先做 A，有了 P3 以后两条路都收。

## P3 子 agent 的双向通道（解决 F3）

Node 在 `session/new` 和 `session/load` 时，往 `mcpServers` 里加一个 stdio 服务：`sous mcp --run <id> --home <home>`。它通过 daemon 的 IPC 只做三件事：

| 工具 | 作用 |
|---|---|
| `report_progress(text)` | 更新 Run 的进度行（任务卡和主管的环境说明里能看到），不叫醒主管 |
| `ask_supervisor(question, options?)` | Run 进入暂停（复用 `pause`），发 `trigger.fired`（kind `question`）给主管；主管用 `run_message` 回答（`followUp` 会恢复暂停的 Run），也可以 `notify` 用户、让用户来答 |
| `report_result(...)` | P2 的结构化结果（D2-B） |

- 安全：这个 MCP 只能发文本，不读文件、不执行命令，权限按 `policy` 的新类别 `sous` 直接放行。服务器上同样可以用。
- 兼容：Claude Code、Codex、Gemini、OpenCode 的 ACP 适配器都接受 stdio 的 `mcpServers`，Kiro 和 Cursor 需要实测。不支持的 agent 照旧工作，只是没有这三个工具。
- 一个 Run 最多问 3 次，超过返回“自己判断并在结果里写明假设”。

> **D3 要不要做双向通道**
> - A（推荐）：做，三个工具都上。
> - B：只做 `report_progress` 和 `report_result`，不让 agent 提问（agent 照旧在结果里写“需要决定”）。
> - C：先不做，P1 和 P2 先上线看效果。

## P4 在对的机器上执行（解决 F4、F5）

**P4.1 路由仍然只是偏好，但不再悄悄发生（已拍板：不做硬规则）。** 条条大道通罗马：从开发机 ssh 部署、在服务器上就地部署、走 CI 都是合法的路，由主管按场景选。router 保持 `Prefer`；运维任务退回到开发机时，`Choice` 带上 `Fallback` 说明（“没有服务器登记了这个项目，派到了开发机 X”），写进任务的派发结果和主管的工具结果，主管自己判断要不要换路。

**P4.2 选不到机器时说清楚。** `task_create` / `task_dispatch` 的结果里写明选中的机器和原因；排队的原因是永久性的（没有目录、agent 不可用）时，工具结果里直接说，并列出可以走的路（clone 到某台机器、指定机器、换 agent），P1 也会叫醒主管。

**P4.3 项目可以放到服务器上。** `project_clone` 允许 clone 到服务器（必须写明 machine），放到服务器 node.json 里的新字段 `deploy_root`（默认 `/srv`，必须在本地配置，Hub 不能改）。git clone 照服务器规则交给用户批准。clone 完成后，主管用 `machine_look` 看仓库里的部署脚本，再用 `project_put` 填 deploy；不确定部署命令时问用户。

**P4.4 ssh 到已接入的机器时给出另一条路（提示，不拦）。** `ssh` 仍是硬信号，照旧交给用户审批（安全规则不变）。Hub 认出目标是已配对的机器（按机器名、主机名、上报的地址）时，在审批卡片上加一句“这是已接入 sous 的机器 X，也可以让主管把任务直接派到 X 上”，选择权在用户。

**P4.5 提示词。** `task_create` 的描述从“交给用户电脑上的编程 agent”改成“交给某台机器上的 agent”；系统提示加一条：“操作作用在哪台机器，就在哪台机器上执行；部署、查服务器的问题，先确认服务器上有这个项目和可用的 agent。”

> **D4 运维任务的路由**：已拍板 B，保持“优先”，退回开发机时报告并提醒主管，不做“只能”。

> **D5 服务器上的 clone**
> - A（推荐）：允许 clone 到 `deploy_root`，并经用户批准。
> - B：不允许，只在页面上手动登记服务器目录（现状，主管只能叫用户去做）。

> **D6 ssh 到 peer**：按设计原则改为提示，不拦（P4.4）。

## P5 返工接着原来的会话（解决 F6）

返工、重试、补充说明后再派发时，如果下一轮落在同一台机器、同一个 agent 上，并且 agent 支持 `session/load`，就 `ResumeSession` 上一个工作 Run 的会话，提示里只写新的要求（“验收意见：…”或“主管补充：…”）。换机器、换 agent 或加载失败时，退回现在的做法（全新会话，加恢复说明）。

> **D7** A（推荐）：做。B：不做。

---

## P6 主管模型（配置，不改代码）

调度大脑比执行 agent 更需要推理能力。建议：主管用最强的模型（比如 Opus 5.5 或同级），审批员和巡检员用便宜的快模型（它们输出的是结构化判断，现在默认跟主管用同一个），验收跟主管一样。

> **D8** 主管和其他角色用什么模型，由你在模型设置页定。

---

## 不建议做的

- **`task_wait`（主管在一轮里等任务结束）**：会占住这个对话的 worker，用户插话要排队，还有超时的问题。用 P1 的事件驱动代替。
- **主管直接执行命令**：违背 0002 和 0024 第 5 条。`machine_look` 只读，加每轮上限，已经够用了。
