# Sous：产品 App 与可组合模块

状态：目标设计与分期实施。已落地的范围以及待通过的发布门槛见[验收记录](acceptance.md)。

配套：[讨论结果](discussion-results.md) · [新架构图](architecture.md) · [实施与验收任务](tasks.md)。

## 1. 目标

**App 是用户安装或部署的完整产品；模块是 App 装配的能力。Hub 是 agent 的工作环境，不是 agent 本身。** 默认桌面版可以随包提供 Hub、Sous Agent、Node 和 WebUI；随包不等于写死依赖，用户可以禁用 Sous Agent，也可以用另一个 ACP agent 接任主管。不装 agent 的 Hub 仍能管理数据和执行已获授权的规则，不能凭空产生 AI 决策。

| 模块 | 拥有 | 不拥有 |
|---|---|---|
| Hub | 对话及可迁移上下文、记忆、项目、任务、Run、审批、事件、定时触发；提供业务 API、MCP 工具和 ACP 客户端接入 | 模型推理循环、默认模型供应商、工作区 shell、文件执行权限 |
| Sous Agent | 可选的第一方 ACP agent；拥有供应商适配、模型调用、工具选择、规划和判断；通过 Hub 工具读取和变更业务数据 | Hub 数据库、任务状态机、审批授权、Node 执行凭据 |
| Node | 机器能力、工作区、执行端 agent、Run 的实际执行、本机权限检查和结果上报 | 全局业务状态、主管角色或 Hub 写入权 |
| WebUI | 聊天、项目、任务、审批、设置等界面；按 Hub 报告的能力显示入口 | Agent 进程、项目或任务业务规则 |

主管是给**某个已登记的 ACP agent 实例**的角色绑定，不是某种模型、内置组件或某台机器的身份。首版每个 Hub 只绑定一个主管，可不绑定；同一个 agent 产品也可以被配置为执行端，但身份、会话、工具范围分别发放。多机部署中持租约的机器是 **Hub 宿主**，它和主管 agent 是两件事。

## 2. 组合方式

| 产品形态 | 内含模块 | 行为 |
|---|---|---|
| Sous Desktop | Hub + WebUI + 本机 Node + 可选随包 Sous Agent | 默认是完整本地产品，能在应用内打开工作台。可改用本机验证通过的第三方 ACP agent；不要求用户先配对 Relay 或部署 WebUI。模型是否需要联网取决于所选 agent。 |
| Hub 服务 | Hub + 可选 ACP 端点 | 无 GUI 也能提供接口；不绑主管时可以手动管理和审批。需要执行时可连接独立 Node。 |
| Sous 托管工作区 | 常在线云 Hub + WebUI + 可选云端主管 | 由云 Hub 持有该工作区的权威状态，手机可手动建任务、审批和派发给仍在线的 Node；本地主管离线不阻塞手动操作。云端主管作为可选模块，不依赖用户电脑在线。 |
| 云工作机 | 云 Node + 执行端 ACP agent | 可选执行机器，按需为允许上云的任务启动。无需维持常驻计算实例，不是 Hub 宿主，也不接管其他机器的本地项目。 |
| 执行端 | Node | 连接已有 Hub，无需本地 Hub 或 WebUI。 |
| 浏览器工作台 | WebUI | 连接已有 Hub，不另起 agent 或 Node。 |

首版由 App 入口显式装配几个预置组合，负责启动、探活、停止和权限配置；**不做动态库加载、插件市场或通用插件框架**。模块可以同包、同二进制或跨进程，但不能跨过业务接口直接拿其他模块的内部对象或写它的存储。桌面版可共用现有 Go 运行时产物，并打包 `build/web` 产物；运行时模块不等于新增 `apps/*`，现阶段不搬目录、不改 Wok 布局。Relay 继续作为可选的多机传输层，不升级为本地桌面版的必需模块。

配对模式仍打开配置的页面，旧 `sous daemon` 仍要求配置 Relay。新的桌面本机工作台使用随包 WebUI 与独立 `sous hub`；当前本机已启用业务管理、内置主管切换及 Apple Silicon 独立沙盒执行，不接入远程 Node。完整本地桌面形态需要新增本地装配入口和本地 WebUI 认证接入，不能靠把静态文件塞进旧包就完成。桌面用受控的本机身份通道，不把 localhost 当成已认证用户；远程模式保留现行配对、Passkey 和适用的租约机制。

## 3. ACP 负责会话，MCP 负责工具

完整模块与部署关系见[新架构图](architecture.md)。

- **Hub → 主管**：区分用户消息与系统事件（例如任务完成、计划触发）；Hub 决定何时排入回合，agent 决定如何回复或操作。适配器把 ACP 更新映射成现有 Hub 对话事件。首版沿用本机 ACP v1 stdio 客户端，优先走候选 agent 实测通过的方式；远端 ACP 传输不挡首版。
- **主管 → Hub**：用 ACP `session/new` 的 `mcpServers` 配置受限工具桥。首版先走 MCP stdio，不把 HTTP MCP、会话加载或系统提示扩展当成门槛。通过真实工具调用验证候选 agent，而不是看到握手成功就允许设主管。工具走同一个领域服务和同一套校验；不解析自然语言或伪造 ACP 流式事件来修改业务数据。
- **身份与工具权限**：由 Hub 绑定 agent 实例、作用域、回合与授权；会话工具凭据限时，可撤销，不让 agent 自报身份或任意扩大项目范围。MCP 桥不是 Hub 管理凭据，也不是现有 worker 的 `sous mcp` 权限。主管不获得工作区、终端或 Node 凭据。第三方 agent 自带工具不会因为接入 ACP 而消失：只允许用户明确批准的程序和参数；验证运行环境能限制工作区、敏感环境变量及内置执行工具。空目录、提示词、ACP 权限回调都不是操作系统隔离；不能落实边界的接入标为不支持主管，不能冒充「纯大脑」。
- **无主管 / 无 Node**：无主管时，界面和 API 仍可查看历史、编辑记忆或项目、手动建任务与审批；需 AI 处理的回合明确显示待处理，不伪装成用户消息，不偷偷启用内置模型。无 Node 时，主管仍可对话、查询和规划，执行任务显示等待合适的 Node。

协议参考：[ACP v1 初始化](https://agentclientprotocol.com/protocol/v1/initialization.md)、[ACP v1 会话与 MCP 配置](https://agentclientprotocol.com/protocol/v1/session-setup.md)。

## 4. 切换主管，不迁移业务数据

- **权威状态在 Hub**：现有项目、任务 ID、聊天、审批、记忆及事件留在原处。ACP `sessionId` 是当前 agent 的私有会话引用，缓存可选，不用于跨 agent 或跨宿主恢复。新主管用 Hub 按作用域提供的角色说明、线程摘要与近期对话启动，按需调用项目、任务和记忆工具；不承诺继承供应商私有对话、内部推理或上下文缓存。
- **切换在回合边界提交**：先探测候选，失败继续用原主管；成功后停止给旧主管分配新回合，等在途回合收尾或显式取消，再提交新绑定并撤销旧工具权限。迟到的输出和工具写入按主管绑定代次拒绝，远程模式还校验 Hub 任期。队列、已经落地的业务变更和 Node 上的 Run 原样保留；失败重试先确认已提交的业务效果，不盲目重跑写操作。
- **Hub 持有记忆，主管挑选内容**：共用既有记忆领域与事件机制。长期记忆的作用域、固定项、来源和归档规则沿用 独立长期记忆提案的方向；选择、更新、整理记忆由主管调用受限工具，不为某个 agent 另建记忆库，也不要求先做完记忆改版才切主管。

## 5. 从现状切入，不重写整套系统

重构前，`apps/core/internal/hub/hub.go` 在 `hub.Open` 里无条件装配 `models.Registry` 和 `supervisor.New`。这部分已迁入可选 `legacyagent`；`internal/supervisor` 既做模型循环，也做消息编排、上下文和部分 HTTP 路由。`internal/task` 的审核与自动审批、`internal/inspector` 的巡检以及摘要整理还有独立的模型依赖。只把 `supervisor.New` 挪走并不能让 Hub 成为纯工具箱。可复用的是现有事件库、任务/审批领域、Node－Hub 协议、`internal/acp` 和 `internal/sousmcp` 的工具桥模式。

1. **先让 Hub 在无主管下成立。** 把回合队列、业务工具、历史/上下文归 Hub，把推理循环移到可选运行器。用一个有窄接口的旧实现适配器保持现行功能，不把过渡适配器变成新 Hub 的必装依赖。先把 `memory_search`、项目元数据读取、`task_create` 露成同一业务层的 MCP 工具。项目元数据由 Hub 提供，不依赖 Node；仓库内容仍由 Node 按权限提供，不混用现有读文件的 `project_read`。用现有 SQLite 数据验证无主管启动、手动管理和旧线程可读。
2. **走通可换的同一条链路。** `用户消息 → ACP 回合 → 查 Hub 记忆或项目 → 建任务 → Hub 派发给 Node → 结果回 Hub`。用假 ACP agent 测时序和异常，再用实际候选测试工具注入、取消与权限隔离。把现有主管的推理部分做成可选的 Sous Agent ACP 入口；它与第三方用同一契约。演示原生 Sous Agent 和一个验证过的外部 agent 互换，并验证旧线程、已有任务、运行中的 Run 仍在。
3. **清点并迁出剩余模型依赖。** 审批政策、任务状态机和巡检计时归 Hub；AI 审批/验收建议、摘要生成等判断是可选能力。没配能力时走人工审批/验收、结构化上下文加近期消息、确定性巡检规则等显式降级；不把主管默认变成能批准自己请求的审批者。接通后再退役旧直连模型路径和相应设置，不更改已有业务数据的所有者。
4. **交付完整桌面包。** 在不依赖 Relay 和托管页面的情况下，以真实本地装配打开 WebUI、跑 Hub 和 Node、设置主管；同时跑一轮旧部署和数据的兼容验收。产品设置展示「主管」「执行机器」「连接」，而不是要求用户理解所有内部模块或维护通用插件清单。

首个里程碑不是改目录，而是：**关闭主管，Hub 照常工作；换一个主管，同一项目和执行中的任务照常工作。** 本机执行的发布资格由沙盒验收决定，具体阶段见[任务文档](tasks.md)。

## 6. 云工作机按需启停

**常在线的是托管 Hub，不是用户的云工作机。** 云 Hub 接收并持久化手机或主管发来的任务；在没有任务时，云工作机仍是可选的逻辑执行目标，但不占常驻 CPU 和内存。首版同一工作区可复用一台隔离的 Linux 云工作机，不做每用户常驻 VM、远程桌面或多云编排。

1. **仅可执行任务触发启动。** Hub 先完成目标选择、项目上云授权、启动前必需审批及配额检查，并持久化任务与启动意图。一旦有可执行任务选中云工作机，云端控制器按需启动或复用实例；打开页面、发聊天消息、建草稿、等待前置审批或等待指定本地机器，都不唤醒云工作机。控制器负责云资源生命周期，不拿项目业务权限；Agent 不持有云厂商管理凭据。
2. **准备就绪才派发。** 预构建镜像带上 Node、执行端 agent 和通用工具，实例用短时引导凭据注册并通过健康检查；项目材料和最小权限凭据按授权按需加载。界面区分「启动云工作机」「准备项目」「执行中」与「启动失败」；启动超时继续保留任务，有限重试后显示失败原因，不无限创建实例。记录冷启动、项目准备、开始执行三段耗时和空闲计算用量，用真实项目的 P50/P95 决定是否值得预热，首版不养常驻热池。
3. **短暂保活，空闲归零。** 没有可执行队列、在途 Run 或临时保活授权时开始空闲倒计时；可先试 5 分钟后回收计算实例，再按实测调整。只有 Hub/Node 确认必要状态已持久化才回收。Run 内部仍在等用户审批不等于空闲；首版不给运行中的进程做透明休眠，只能在 Run 结束或按明确超时规则安全停止后回收。若新任务在排空阶段到达，能取消回收就继续复用，否则保留任务并唤醒新实例。
4. **计算可销毁，工作成果不能。** Hub 持有任务、进度和审批。未提交改动及用户需要的文件必须先保存在工作区的独立持久存储，或已成为 Hub 管理的可恢复产物；确认失败时标明原因并保留现场，不把该 Run 当成已安全回收。临时缓存和进程内存不承诺恢复，重建时重新获取凭据。持久存储的保留期、删除规则和费用与计算分开呈现；任何保留现场导致的继续占用也要可见。
5. **重试不应重复创建或重复派发。** 启停意图跨重启可恢复，按工作区和实例代次做幂等、对账与孤儿实例清理；回收前阻止派发给旧实例，一次 Run 只绑定一次有效派发。对执行结果不确定且可能已产生副作用的旧 Run，先对账再决定是否重试，不重放命令来假装恢复。首版设启动与运行上限、配额和可取消入口。

**验收**：所有个人电脑关机时从手机给云工作机派发授权任务；从零实例唤醒，任务完成后回收计算；下一条任务重新唤醒并能读回此前保留的成果。并发来单、控制器重启、云 API 超时、回收时来单，以及审批挂起都要有测试。本地专属任务不被迁到云端。

## 7. 本地 Node 的沙盒和联网

**首版使用 Microsandbox 作为本地 Node 唯一的 microVM 后端。** 不开发 SmolVM 适配或回退，不采用 Terrarium 或 Docker 运行依赖。PoC 验证选定版本在目标平台上的生命周期、项目按 Run 导入与清理、宿主撤权与崩溃兜底、无公网出站时的宿主–Guest 通道、受限出站与实际启动耗时。首版不依赖热挂载；未通过验收的平台不开放云端控制本机 Node，不回退到宿主裸跑。此处只限定本地 Node，云工作机另行选型。

- **云 Hub 只派任务，不授予宿主权限。** 本机授权器保存用户选择的文件或目录，按项目授权 ID 和有效期限判定访问，不接受云端传来的任意宿主路径。Node、执行端 ACP agent、终端与文件工具在 Guest；宿主只保留窄接口的授权、任务接入和 VM 生命周期管理。不能用终端、文件预览、Git、配置或维护 API 绕过这个边界。本地 Hub 是否沙盒化另行决定。
- **默认按 Run 导入、在 Guest 内写、在本机审阅后写回。** 任务完成、取消或到期后释放 Guest 和临时项目材料；不以停机暂停冒充撤权，也不复用包含项目数据的预热快照。实时挂载另做；需明确区分只读、实时写和限时无人值守授权，热撤销失败时由宿主终止 VM。
- **控制通道不等于 Guest 上网。** 宿主小型接入组件主动连 Hub 所在工作区入口或对应 Relay；不要求用户开公网端口。通过本机受限 IPC（如支持的 vsock 通道）把任务和结果交给 Guest；不转发宿主文件系统、通用代理或管理 socket，也不依赖 Hub 在 VM 停机时直连它。Guest 默认不通公网或宿主局域网；必须联网的模型与依赖另按本机策略放行。纯离线配置须验证模型和工具均能离线工作。任务结果的上报范围和模型输入仍决定哪些数据会离开本机；目录只读不能阻止内容通过授权通道发出。

上游参考：[Microsandbox Go 网络策略](https://docs.microsandbox.dev/sdk/go/networking)。据上游文档，拒绝全部网络流量不影响其内置宿主–Guest 通道的 Exec/FS；Sous 的任务消息通道和异常清理仍需在真实设备验证。优先验证 Go SDK 集成，具体版本、所需调用与分发方式以 PoC 结果为准。

## 8. 网络拓扑与延迟预算

**模块可替换不等于每个模块都必须是一项远程服务。** 每个工作区只有一个权威 Hub；交互默认是星型，不让浏览器寻找 Agent/Node，不让 Node 互相转发，也不默认做跨区双写。同一工作区的浏览器与桌面看到同一套状态。静态前端部署位置和 API 路径独立，页面从 CDN 下载不意味着聊天流需要再经过前端部署所在的服务。

| 组合 | 交互热路径 | 首版取舍 |
|---|---|---|
| 纯本地 | 桌面 WebUI ↔ 本机 Hub ↔ 本机主管；需要执行才联系本机 Node | 本机 IPC/loopback，不绕云或 Relay。是否访问公网模型是单独选择。 |
| 云 Hub + 云主管 | WebUI ↔ 工作区云入口 ↔ Hub ↔ 主管；主管查 Hub 数据走本地工具桥 | 托管默认：第一方主管是隔离身份的同机进程或同区域服务，Hub 数据层同区域部署。页面可走 CDN，实时 API/事件流不经过额外前端应用服务；交互主管的热状态与按任务启停的云工作机分开。 |
| 云 Hub + 任意 Node | 手动或主管建任务后，Hub ↔ 选中的 Node；Node ↔ 执行 Agent 留在同一执行环境 | Node 派发与聊天分开；普通聊天、读项目元数据不等待 Node。云工作机默认同区域按需唤醒，本地 Node 离线则任务明确等待，不自动把项目搬上云。 |
| Hub 与主管一端在云、一端在本机 | 回合和 MCP 工具都可能过 WAN；如果 Hub 在家，远程 UI 还需要连到家庭 Hub | 高级模式。用认证的单一 Sous 接入链路连接主管适配器，目标 Agent 仍可在本地走 ACP stdio；不可用时提示等待，不静默切换主管。家庭 Hub 掉线时，云主管不能替代它的状态。先交付本地与托管，再验证此组合。 |
| 外部 Agent 客户端 | 外部客户端 ↔ Hub MCP；执行任务仍由 Hub 派给目标 Node | 不把每次外部工具调用转给主管，不为各客户端另建一套项目状态。 |

托管工作区绑定一个主区域，按主要用户、执行环境、模型服务的实测和数据驻留选择；需要现有盲中继的模式保留其认证和加密语义；托管时优先让 Relay 与 Hub 就近，自托管按家庭 Hub 和主要客户端间的实测路径选入口，不叠加额外业务转发。托管入口是否复用现有 Relay 应按接入验证和实测决定，不能为省一跳而绕过授权。首版不做多区域工作区状态复制或自适应直连/中继切换。[ACP v1 标准传输](https://agentclientprotocol.com/protocol/v1/transports)是 stdio；远程主管不要求第三方原生监听公网端口或支持尚在提案中的标准远程传输。

### 热路径设计与验收

1. **不让 WAN 延迟按工具调用次数累加。** Hub 快速持久化消息并确认，异步运行回合和派发。复用 WebSocket、Node 可靠通道；同区域内交互照样流式。一个权限范围内，把无依赖、会反复读取的项目/任务元数据按需批量提供，避免调用细粒度工具逐个取字段；不为了省请求而合并独立授权或提前读取项目文件。执行端 ACP、Git、文件系统操作就地运行；不把逐文件访问做成跨 WAN 的 RPC。
2. **流式输出和可靠状态分开。** 沿用 `/ws?since` 与 Node 的序号、确认、重发和去重。回复增量不等每段落盘或确认，断线以重放持久事件和获取最终回复恢复；不能用重发消息来重做有副作用的调用。大 diff、附件或日志传输不得阻塞审批、取消和聊天；先限速/限队列，必要时分离传输通道。代理需验收保活、超时以及流式输出是否被积攒。
3. **分别计时，而不是用一个「感觉慢」指标升级机器。** 以 `message_id`、`turn_id`、`run_id` 关联浏览器的「发送 → 已保存 → 首段正文 → 完成」，以及 Hub 排队/持久化、Agent 回合、MCP WAN 次数与 RTT、模型首输出和增量送达；另测「任务已排队 → Node 接收 → VM/项目就绪 → 首进展」。断线恢复和冷启动分别统计，记录 p50/p95。拓扑不同分别对比，不把模型耗时当网络耗时。
4. **PoC 先模拟再测真实线路。** 相同脚本用假 Agent 重复跑：无工具聊天、含依赖的多工具回合、派发/审批/取消，以及断线重连和大 diff 并发；比较本地、同区域、约 80/180 ms RTT 与抖动场景，再用真实 Agent/模型测端到端。可先设暖连接、80 ms RTT 的内部验收目标：提交到持久化确认 p95 ≤ 300 ms（不含人工审批或模型），模型首段文本耗时、冷启动耗时另定基线。这些是拟测目标，不是实测或产品 SLA。

优先级：**减少串行往返 → 部署就近 → 验证反代和连接配置 → 按指标扩容。** 提升服务器规格只处理已测出的 CPU、I/O、连接容量或队列瓶颈；不会缩短公共网络往返、等待用户电脑上线或模型供应商响应。
