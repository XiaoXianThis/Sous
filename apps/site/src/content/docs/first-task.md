当你的 Hub 已经启动、至少接入了一台在线的开发机（且 `sous agents` 显示至少有一个编程 Agent「已登录」）后，就可以开始跑第一个任务了。

在 `sous` 里，**你只和主管（sous）对话**。你不需要手动填复杂的流水线表单，主管会根据你的意图判断是先查一下回答你，还是创建任务派给子 Agent 去干活。

## 1. 先把项目加到工作台

**为什么先登记项目**：项目记录了一个 Git 仓库在哪台电脑的哪个目录、默认用哪个预设（Agent + 模型）以及部署到哪台服务器。登记后，主管才知道去哪里读代码、在哪里拉分支。

你有三种方式把项目放到工作台上：

1. **从工作空间自动发现**：配对电脑时设置了 `--workspace ~/Code`（或在「设置 → 机器」中设置工作空间），daemon 会自动向下扫描两层 Git 仓库。点击工作台顶部的 **+ 项目**，可直接把发现的仓库登记为项目，或直接对主管说「把我电脑上的 `xxx` 仓库加为项目」。
2. **让主管新建一个项目**：在对话里说「帮我在笔记本上新建一个叫 `my-tool` 的项目（用 wokspace 结构）」，主管会调用 `project_create` 在开发机第一个工作空间里执行初始化并自动登记。
3. **不针对具体仓库的杂事**：如果你只是让它写个一次性脚本或查个通用问题，主管会自动把任务归入内置的 **`misc`（杂项）** 项目，在 `~/.sous/scratch/<id>` 临时目录中执行。

## 2. 怎么跟主管说话（讨论 vs 动手）

你可以在**右侧主线聊天栏**、**项目弹窗右侧的「项目对话」**，或者本机终端的 **`sous chat`** 里跟主管说话。

### 小技巧：让主管准确知道你在说哪个项目

- **用 `@项目名` 引用**：在输入框里键入 `@`（行首或空格后）会弹出激活项目的候选列表，选中后消息会带上准确的 `project_id`。
- **打开项目弹窗再发消息**：当你正在查看某个项目或某条任务时，发出的消息会自动附带当前工作台上下文（`context.project_id` / `context.task_id`），直接说「把这个任务重试一下」或「帮我看下这个仓库的构建脚本」，主管就能明白「这个」指什么。
- **使用项目专属对话**：点开项目卡片进入项目弹窗，打开右侧的对话栏。这里的对话**作用域严格锁定在该项目内**，不用每次提项目名字，也不会误动别的项目。

### 讨论阶段：主管不会一上来就乱改代码

当你问一个问题或探讨方案时，主管会按深度选择工具：

1. **一两个文件或机器状态**：主管直接调用 `project_read`（读文件、列目录、grep 正则搜索）或 `machine_look`（在目标电脑上执行一条 20 秒超时的只读命令，如 `docker ps`、`systemctl status`），几秒钟内直接回答你。
2. **需要通读代码库、连续推敲方案**：主管会调用 `consult` 唤醒该项目所在开发机上的**项目顾问**。项目顾问是一个强制处于 `readonly`（只读）档位的常驻 Agent 会话，不占机器并发槽位；它的回答会在聊天中以左侧带色条的「`agent · 顾问 · 项目`」消息原样呈现。

## 3. 任务怎么被拆解与派发

当你聊清楚方案、说「好，按这个改吧」或直接下达明确指令（例如：「在 `@Sous` 里给 `apps/site` 加上 `/changelog` 页面，跑通 `bun run build`」），主管会创建任务并派发执行。

对于较大或有先后依赖的需求，主管会拆成多个任务（可通过 `depends_on` 设定前置依赖，前一个完成自动触发下一个）。每个任务在派发前由主管定下四个关键属性（详见 [主管、子 Agent、任务与执行位置](/docs/core-concepts)）：

1. **在哪儿做（`place`）**：
   - `worktree`（代码任务最常用）：在 `~/.sous/worktrees/<仓库名>/<短id>` 拉出独立分支 `sous/<slug>-<短id>`，完全不碰你原来的工作区。
   - `in_place`：直接在项目目录里就地修改，动手前自动在影子仓库拍快照，支持一键恢复。
   - `scratch`：在 `~/.sous/scratch/<短id>` 临时目录里执行。
2. **从哪儿开始（`base_branch` + `base_from`）**：当使用 `worktree` 时，主管会明确指定基于本地分支（`local`）还是先 `git fetch` 后基于远端 `origin/<分支>`（`remote`）切出任务分支。
3. **谁来做（预设 `persona_id` 与 `model` / `effort`）**：如果先找过「项目顾问」讨论，主管创建任务时会带上 `from_consult`，让刚才已经读懂代码的同一个 Agent 会话无缝接着写代码，不浪费时间和 Token。
4. **要不要验收（`review`）**：调研和小改动默认不额外验收（`none`）；大改动可选让验收模型看 diff（`model`）、派只读验收 Agent 跑测试（`agent`）或交由你亲自验收（`user`）。

## 4. 怎么处理权限审批与中途插话

任务派发后，工作台项目卡片上会展开一张实时 **Agent 卡**，显示当前运行的预设、Agent、模型、所在电脑，以及最新两行工具调用或进度。

### 原地审批（ApprovalStrip）

在默认的 `auto`（自动审批）模式下，常规读写、工作树内编辑、跑测试以及无高危信号的常规命令会由本地策略或审批 Agent 自动處理。只有当操作命中**硬信号**（如读密钥、外发数据、`ssh`、改系统服务）或审批 Agent 拿不准时，才会找你拍板：

- **在工作台卡片上直接批**：审批不会刷屏聊天记录，而是直接出现在工作台对应任务行或 Agent 卡的原位置上，点 **允许这一次** 或 **拒绝** 即可。
- **在任务详情页选更多选项**：点击卡片打开任务详情，可以看到完整的命令、触发的风险信号片段以及审批 Agent 已经查过的证据，并可选择 **始终允许（`allow_always`）**（在同一任务、同一执行身份下复用）或填写附言说明拒绝原因。
- **在终端里批**：如果你开着 `sous chat`，输入 `/approvals` 查看列表，用 `/approve 1` 或 `/reject 1 换个方式` 即可批复。

### 中途补充要求或回答子 Agent 的问题

- **子 Agent 主动问你**：子 Agent 遇到需求有两种理解或缺少配置时，会调用内置的 `ask_supervisor` 工具提问。问题会叫醒主管（主管能答的自己答，拿不准的转问你），你直接在对话里回复，或者在任务详情页底部的输入框发一条补充说明，等待中的子 Agent 就会立即收到并继续往下做。
- **随时追加指令**：即使子 Agent 没提问，你看到它方向偏了，也可以随时在任务详情页发追加指令（或暂停 Run 后再恢复）。

## 5. 怎么看结果与按需 Git 交付

### 查看结构化结果与 Diff

当子 Agent 完成工作后，它会提交一份包含五个固定维度的 **`## 结果`** 汇报，同时叫醒主管：

- **做了**：完成了什么功能或修复
- **改动**：改了哪些文件或执行了什么命令
- **验证**：跑了什么测试或构建命令、结果如何
- **没做完 / 风险**：遗留问题或需要注意的边界
- **需要决定**：需要你拍板的事

你可以在聊天栏直接读到这份汇报，也可以点开任务详情查看完整的 **Diff 对比**、每个工具调用步骤与耗时，或者在项目弹窗的 **详情** 标签页里直接浏览和预览生成的文件。

### 按需执行 Git 操作（绝不越权自动合并）

任务变成「已结束」时，**改动仍然安全地停留在任务分支上（`git_state: unmerged`）或就地目录里**，`sous` 绝不会未经你同意就合并到主分支或推送到远端。

当你确认结果满意后，只需在对话里跟主管说一句话：

- **「帮我合并到 `main` 并推送到远端」**：主管依次调用 `git_merge`（先在 worktree 内 rebase，再对目标分支做 `--ff-only` 快进合并，有冲突则安全中止不污染工作区）与 `git_push`。
- **「帮我推上去开个 PR」**：主管调用 `git_pr` 推送任务分支并用 `gh pr create` 创建 Pull Request，返回 PR 链接。
- **「把刚才那次合并撤回来」**：只要还没有推送到远端，主管调用 `git_undo` 即可将分支还原并恢复原来的任务分支；如果是就地任务（`in_place`），说「撤销这个任务的改动」就会调用 `task_restore` 按快照精准还原任务改过的文件（你自己在工作区改的文件不受影响）。
