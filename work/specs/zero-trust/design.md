# 设计：零信任（0.3.0-alpha1）

需求见 `requirements.md`。本文中的“用户”就是 sous 唯一的使用者。标 **[M0]** 的地方要先在第一个里程碑里实测，结果可能改变本文的选择。

## 0. 已拍板

| # | 决定 |
|---|---|
| D1 | Hub 改成**中继**：只转发和存放密文，没有任何密钥。主管等“思考”的部分搬到用户指定的**大脑机器**上（取代 0002） |
| D2 | 信任根是用户的 **Passkey**（推荐 iCloud 钥匙串或 Google 密码管理器同步）。没有主密码，**不设恢复码**；Passkey 全部丢失时，聊天等数据作废，Node 在本机重新配对 |
| D3 | 启动 app **解锁一次**，到退出或自动锁定为止。自动锁定时间可在 1 分钟到“永不”之间调，默认 15 分钟 |
| D4 | 授权分三档：范围内（大脑自己签）、范围外（用户点一下）、关键操作（用户刷 Face ID，由验证方自己核对断言） |
| D5 | **大脑机器由用户指定**，按优先级加租约自动选出中心；不做多数派共识，**不做双脑会签** |
| D6 | AI 自己发起的任务**不需要确认**，只受项目自主范围限制。不做任务锚定，也不设频率上限（0031） |
| D7 | 一台普通 Node 被攻破不影响其他机器；踢出是关键操作，冻结和全部暂停只要会话签名 |
| D8 | 页面托管在 **Vercel**，用用户自己的域名，只从本机部署 |
| D9 | 项目文件不加密 |
| D10 | 发布签名用离线密钥，Node 只装签过名的版本；仓库地址写死 |

## 1. 总体结构

```
          ┌───────────── 用户的设备（PWA，Vercel 托管）─────────────┐
          │  Passkey → 身份密钥 → 会话密钥；本地缓存（密文）       │
          └──────────────┬───────────────────────────────────────┘
                         │ WSS（内层是端到端加密的信封）
              ┌──────────▼──────────┐
              │ 中继（sous-relay）  │  转发、信箱、密文日志、配对会合点
              │ 没有任何密钥         │  看得到：谁、何时、多少字节
              └───┬─────────────┬───┘
                  │             │
        ┌─────────▼───┐   ┌─────▼────────┐
        │ 大脑机器 ×N  │   │ 普通 Node ×M │
        │ sous daemon  │   │ sous daemon  │
        │ + 大脑模块   │   │              │
        └──────────────┘   └──────────────┘
```

- **中继**由现在的 `sous-hub` 改造而来，二进制改名为 `sous-relay`。它只保留连接管理、信箱、密文存储、配对会合和健康检查。
- **大脑模块**由现在 Hub 的业务代码整体搬过来：supervisor、task、router、trigger、inspector、eventlog、store、provider、mcp、web、notify、sysmap、prompts、tool。它编进 `sous`，只在被指定为大脑、并且持有租约的机器上运行。
- **页面**不再由服务器托管，而是部署到 Vercel。原来走 HTTP 接口的那些功能，改成发给当前大脑的加密 RPC（§8.5）。

## 2. 密码学选型

| 用途 | 选择 | 原因 |
|---|---|---|
| 签名 | ECDSA P-256（SHA-256） | Passkey（ES256）、Secure Enclave、TPM、WebCrypto 的不可导出密钥都原生支持它，私钥可以留在硬件里 |
| 密钥封装 | **X-Wing**（X25519 + ML-KEM-768 混合）走 HPKE（RFC 9180） | 抗量子，防止“现在截获、以后解密”；任何一半被攻破，另一半仍然成立 **[M0：Go 和浏览器端的实现]** |
| 对称加密 | AES-256-GCM，nonce 由计数器派生 | WebCrypto 原生支持，密钥可以不可导出 |
| 密钥派生 | HKDF-SHA-256 | |
| Passkey 派生密钥 | WebAuthn PRF 扩展（`hmac-secret`） | 用 Face ID、指纹、PIN 解锁身份密钥，同步的 Passkey 在各台设备上派生出同一个值 **[M0：各平台支持情况]** |
| 哈希链 | SHA-256 | |

- 签名暂不做抗量子：目前没有“现在伪造、以后生效”的风险，以后可以叠加 ML-DSA。
- 所有签名和密文都带上下文标签（`sous/v1/<用途>`）、发送者、接收者、所属域和纪元，并作为 AAD。这样一条密文、一个签名被挪到别的用途、别的项目或别的接收者那里，都会验证失败。
- 实现只用 Go 标准库、`golang.org/x/crypto`、WebCrypto，再加上一个经过审计的 JS 库补 ML-KEM 和 X25519 的缺口（候选 `@noble/post-quantum`、`@noble/curves`，**[M0：确认审计状态]**）。协议代码集中放在 `internal/trust`（Go）和 `src/trust`（web），两边共用一套测试向量。
- 强度：P-256、X25519、AES-256 都在 128 位安全强度以上，GPU 和 AI 都无法暴力破解。可能被攻破的只有实现和低熵输入，所以：不从口令派生密钥；配对串有 128 位随机数（§4）；唯一的低熵输入是设备 PIN，由安全芯片做防重试。

## 3. 身份、密钥和名册

### 3.1 用户身份

- **身份密钥**（签名用 P-256 和封装用 X-Wing 各一对）只在首次设置时生成一次。私钥用 Passkey PRF 派生出的密钥包装，包装后的密文存在中继上。每个 Passkey 各有一份包装。
- 身份密钥签发名册、会话证书，以及“范围外”的点击批准。
- **Passkey 的公钥**（ES256）也写进名册，用来让验证方自己核对关键操作（§5.3）。
- 增加一个 Passkey（比如一台不同步的 Windows 电脑上的 Windows Hello）是关键操作：由已解锁的设备给它包装一份身份密钥，并把它的公钥加进名册。
- 拿到一台新设备时，只要它能用同一个同步的 Passkey，登录就能直接用，不需要旧设备配合。

### 3.2 会话

1. 解锁时：通过 WebAuthn（`userVerification: required`）拿到 PRF 输出，派生出包装密钥，再把身份私钥解包成**不可导出**的 WebCrypto 密钥，放在内存里。
2. 生成一把不可导出的**会话密钥**，由身份密钥签发**会话证书** `{session_pub, device_label, issued_at, expires_at}`，有效期等于锁定时长，最长 24 小时；选“永不”时每小时自动续签。
3. 日常指令、点击批准都用会话密钥签名，验证方先查会话证书，再查签名。
4. 锁定或退出时：丢弃两把密钥，并广播一条 `session.end`。没来得及广播时（崩溃、被系统回收），证书到期后自然失效。
5. 页面上任何脚本都拿不走密钥本身，只能在页面存活期间使用。这一点也是页面托管必须加固的原因（§9）。

### 3.3 机器的密钥

- 每台 Node 在配对时生成自己的签名密钥（P-256）和封装密钥（X-Wing）。
- 签名私钥优先放进硬件：macOS 用 Secure Enclave，并限定只有签过名的 `sous` 能用；Windows 用 TPM（CNG）；Linux 有 TPM2 时用 TPM2。封装私钥用硬件密钥包装后存盘。没有硬件时退回到文件存储（权限 0600），并在 app 里标注“软件密钥”。**[M0：Go 访问 Secure Enclave 需要 cgo，现在的构建不用 cgo]**
- 这一层只是抬高门槛：拿到 root 也取不走硬件里的私钥，但仍然可以让 `sous` 进程替它签名。S5 和 S6 的保证不依赖这一层。

### 3.4 名册

名册是一份由身份密钥签名、版本号单调递增的文档，验证方据此判断“谁是自己人”：

```
{
  v: 版本号, issued_at,
  user:    { sign_pub, kem_pub, passkeys: [{cred_id, pub, label}] },
  rp_id:   "<页面域名>",
  relay:   "<中继地址>",
  nodes:   [{ node_id, name, sign_pub, kem_pub, key_storage: "hardware"|"software",
              brain: { priority } | null, frozen: bool }],
  prev:    上一版名册的哈希
}
```

- Node 和大脑只接受**版本号更高、并且 `prev` 能接上**的名册，以此防止回滚。中继可以扣着新名册不发，所以踢出操作还会通过信箱直接发给每台机器，并在 app 里显示各台机器已确认的版本。
- 让成员变多、权限变大的修改（加机器、加 Passkey、指定大脑、解冻）必须附带一次 WebAuthn 断言（§5.3）。让权限变小的修改（冻结）只要会话签名。踢出虽然也是收紧，但按用户的要求同样要刷 Face ID。

## 4. 配对

不再使用 6 位配对码，也不用 PAKE，改为**用户自己搬运的高熵配对串**：

1. 用户在 app 里点“添加机器”，刷一次 Face ID（关键操作）。app 生成配对串：`sous1-` 加上 base32 编码的 `{relay 地址的哈希, 身份签名公钥的指纹（32 字节）, 一次性秘密（16 字节）, 过期时间}`，大约 90 个字符，10 分钟内有效。
2. 用户把配对串复制到这台机器的终端里：`sous pair <配对串> [--name ...] [--role ...]`。通过 ssh 粘贴也可以。只有手机在身边时，app 可以用摄像头扫描 Node 在终端里打印的二维码，这时方向相反：二维码里装的是 Node 的公钥指纹加一次性秘密。
3. Node 生成自己的密钥，把 `{node 公钥, 名字, 系统, HMAC(秘密, 全部内容)}` 通过中继发给 app。app 核对 HMAC，Node 核对 app 回送的身份公钥是否和配对串里的指纹一致，同时核对名册签名。
4. app 把这台 Node 写进新版名册（这个配对流程本身已经附带了第 1 步的断言）。

中继在整个过程中只转发，它既不知道一次性秘密，也伪造不了指纹。配对串经由剪贴板或终端传递，不经过中继。

`sous trust reset`（只能在本机执行）会清掉本机的密钥和名册，回到未配对状态。

## 5. 授权的三档

### 5.1 范围内：大脑自己签

**项目自主范围**是每个项目一份、由身份密钥签名的文档（修改它是关键操作）：

```
{ project_id, v, nodes: [node_id], repos: [项目身份键], max_mode: "default"|"auto",
  purposes: ["work","review","git","consult",...], allow_merge: false, allow_deploy: false,
  allow_ops: false }
```

- 当前大脑发出的指令只要落在范围内，Node 就直接执行：Run 落在名单里的机器和仓库上，权限模式不高于 `max_mode`，用途在允许的列表里。
- `open` 模式永远不在自主范围内。
- 默认值：`max_mode: auto`；不允许合并、部署和运维；机器和仓库按项目当时的登记情况填写。
- AI 自己发起的任务和用户在聊天里交代的任务一视同仁，都在这一档里。

### 5.2 范围外：用户点一下

大脑想做超出范围的事，比如合并、部署、在不在名单里的机器上动手，就把**指令本身**发到 app，形成一张卡片。用户点“批准”，会话密钥对这条指令的哈希签名，大脑再把签名附在指令上发给 Node。Node 核对：签名来自一张有效的会话证书，签的正是这条指令。

需要 app 处于解锁状态；锁着时卡片留着，等下次解锁处理。现有的权限审批（`approval.request`）也走这条路，但由 0019 里的确定性规则和审批 agent 自动放行的部分照旧由大脑处理。

### 5.3 关键操作：刷 Face ID，验证方自己核对

关键操作的清单（不可配置）：

- 添加或踢出机器；添加或移除 Passkey；指定或取消大脑；解冻
- 修改项目自主范围
- 以 `open` 模式运行
- 打开终端（`kind: shell`）；远程管理 agent（`node.request`：安装、登录、写 API Key、编辑配置文件）
- 安装更新
- 增删改模型供应商和 MCP 服务（它们决定了 Key 发往哪里、在大脑机器上运行什么）

做法：app 用 `challenge = SHA-256(sous/v1/critical ‖ 指令的规范化编码)` 发起一次 WebAuthn 断言（`userVerification: required`），把断言（`authenticatorData`、`clientDataJSON`、签名、`cred_id`）附在指令上。验证方（Node 或大脑）自己检查以下几项：

- `cred_id` 在名册里，签名能用名册里的公钥验证通过
- `rpIdHash` 等于 SHA-256(名册的 `rp_id`)
- `clientDataJSON.origin` 是 `https://<rp_id>`，`type` 是 `webauthn.get`，`challenge` 和指令对得上
- `authenticatorData` 里的 UV 标志位为 1
- 断言签发后不超过 5 分钟，并且没有用过（按 challenge 去重）

所以，即使页面被替换成恶意页面，它也无法在用户不知情的情况下让关键操作生效：每一次都要用户亲自验证一次，而且签的就是这条指令。页面上展示的内容和实际签名内容是否一致，靠页面托管的加固来保证（§9）。

### 5.4 收紧权限不需要 Face ID

冻结一台机器、全部暂停、取消 Run、结束会话、撤回卡片，都只要会话签名，越快越好。

## 6. 指令信封和验证

所有设备、大脑、Node 之间的消息都是信封：

```
outer（中继看得到）: { to, from, mailbox_seq, size }
inner（HPKE 加密给 to 的 kem_pub）:
  { ctx: "sous/v1/cmd", from, to, chain: { seq, prev_hash }, issued_at, expires_at,
    term?（大脑发出时）, body: {...原来的帧...},
    auth: { kind: "brain"|"session"|"critical", sig, session_cert?, approval?, assertion? } }
```

接收方的检查顺序：

1. 解密成功，并且 `to` 是自己。
2. `from` 在当前名册里，没有被冻结；如果是大脑发来的，它必须持有当前最高任期的有效租约（§8.2）。
3. `chain.seq` 正好是上一条加一，`prev_hash` 能接上。乱序的先缓存；出现缺口时等待，并上报“缺了第 n 条”。重放的消息直接丢弃。
4. 当前时间不超过 `expires_at`（指令默认 5 分钟），容忍 2 分钟时钟偏差。
5. `auth` 和指令类型对得上：范围内用 `brain`，范围外要附 `approval`，关键操作要附 `assertion`（§5）。
6. Node 本地的硬规则（§10.3）检查通过。

被拒绝的指令也写进审计日志，并以加密事件的形式告知用户。

帧的内容沿用 `core-hub-node.md` 里的 `run.start`、`run.message` 等类型，只是外面包了一层信封。其中 `node.update` 只保留 `{version}`，去掉 `repo`。

## 7. 数据加密

### 7.1 域和纪元

- **域**：一组共享同一把密钥的数据。全局有一个**主域**，存放主线对话、笔记、会议、设置、模型 Key、MCP 配置、预设；每个项目各有一个**项目域**，存放项目对话、任务、Run、审批、diff、仓库信息。
- **纪元**：每个域的密钥按纪元轮换。纪元 n 包含一把对称密钥 `K_n`（成员用来读写事件日志）和一对 X-Wing 密钥 `P_n`（公钥公开，供“只写不读”的 Node 写入）。
- **成员**：用户身份（所有设备共用）加上参与这个域的大脑机器。主域的成员是全部大脑机器；项目域的成员是用户为这个项目选的大脑机器，默认是全部。
- 纪元密钥用 HPKE 包装给每个成员，包装后的密文存在中继上。成员会保留所有旧纪元的密钥，以便读取历史。
- **轮换**：踢出成员、把某台大脑移出某个域，都会开启新纪元。被移出的成员读不到之后的任何内容。它以前读过的数据无法收回。

### 7.2 普通 Node 只写不读

- 普通 Node **不是任何域的成员**。它只拿到这次 Run 需要的东西：指令里带着 prompt；它要写入的项目域，只给它当前纪元的公钥 `P_n.pub`。
- Run 的输出、diff、`node.repos` 等内容，Node 为每个 Run 生成一把流密钥，用 HPKE 把它封装给 `P_n.pub`，再用这把流密钥加密数据。大脑和用户的设备都能解密；Node 只认得自己写的那条流，读不到别的。
- 这就是 S5 的数据层保证：攻破一台普通 Node，只能拿到它自己经手的数据。

### 7.3 加密的事件日志

- 大脑现在的 `eventlog` 是唯一的写入者，这个结构保留。每条事件按所属的域，用 `K_n` 加密，然后追加到中继上这个域的日志里。
- 每条日志带 `{域, 纪元, 任期, 序号, prev_hash}`，并由大脑签名。中继只能存，读不懂也改不了，丢掉一段会因为哈希链断开而被发现。
- 大脑机器在本地用 SQLite 维护投影视图（也就是现在的 `store`），可以随时从中继上的日志重建。
- 中继用来做同步的游标、大小和时间戳都是元数据，可以看到。
- 附件（图片、文件）也按同样的方式加密，作为大块数据存放。

### 7.4 推送通知

推送改由大脑直接发送，不经过中继。大脑持有 VAPID 私钥（存放在主域里），按 RFC 8291 把内容加密给浏览器订阅时给出的密钥，再交给推送服务。推送服务和中继都看不到内容，所以通知可以照常显示具体文字。

## 8. 大脑

### 8.1 资格

- 名册里 `brain` 不为空的 Node 就是大脑机器，带一个优先级。指定或取消大脑是关键操作。
- 建议只指定少数几台、干净的个人电脑。app 在用户指定时会提示：服务器、部署目标、软件密钥的机器不建议当大脑。

### 8.2 租约和选主

- 租约内容为 `{term, holder, issued_at, expires_at}`，由持有者签名，有效期 90 秒，每 30 秒续一次，通过中继广播给所有机器和设备。
- 一台大脑机器在看不到有效租约超过 90 秒，并且在它能看到的在线大脑里优先级最高时，就以 `term + 1` 声明新租约。
- 所有验证方只接受**任期最高**、未过期、签名者是大脑机器的租约，并且只执行当前任期的持有者发来的指令。
- 中继可以把网络切成两半，造成两个大脑同时存在。这时任期高的胜出，任期低的一方看到更高的租约就让位，它在旧任期里发出、还没被执行的指令会被拒绝。最坏的结果是重复做事，不会越权。
- 每台大脑机器需要能访问模型供应商；MCP 的 stdio 服务要装在每台可能当大脑的机器上（app 会显示哪些机器缺少哪些服务）。

### 8.3 状态的接力

新大脑上任时：从中继拉取各个域的日志，验证哈希链，重建投影，然后在新任期下继续写入。上任前它会把自己看到的日志头和其他机器、设备上报的日志头对比；发现中继给的日志落后时，先等待并提示用户，不在旧状态上开工。

### 8.4 大脑权限的上限

大脑能签的只有范围内的指令（§5.1），外加它从用户那里拿到的点击批准和断言（只是转发，伪造不了）。它能读的只有它作为成员的那些域。这就是 S6。

### 8.5 app 和大脑之间的 RPC

- 现在的 `core-hub-http.md` 里的接口，保留语义，改成信封里的 RPC：`{method: "GET /threads", body}`，响应也装在信封里。大脑这边用一个适配层，把现有的 `httpapi` 处理函数直接接上，尽量少改业务代码。
- 实时更新（现在的 SSE 或 WebSocket 事件流）改成大脑把事件加密后推给在线的设备。
- 所有大脑都离线时，app 只读本地缓存（IndexedDB，内容用会话期间派生的密钥加密），能做的只有：查看、冻结、踢出（名册操作由设备直接发给各台机器）、全部暂停。

### 8.6 从 Hub 搬到大脑要注意的

- **`web_fetch` 的内网防护更重要了**：大脑在用户家里的网络里，SSRF 可以打到局域网。现有的内网拦截规则保留，并且默认对局域网网段一律拒绝。
- 模型 Key、MCP 的 `env` 和 `headers` 存放在主域里，只有大脑机器能解密。
- 现在 Hub 上的 `sous-hub admin passkey-reset`、`dev-login` 这类后门全部去掉。

## 9. 页面（Vercel）

- `build/web` 用 `vercel deploy --prebuilt --prod` 从本机部署，**不连接 GitHub 自动部署**。Vercel 账号开启硬件密钥两步验证。
- 使用用户自己的域名作为 `rp_id`。以后换托管商不影响 Passkey，换域名才会。
- 严格的 CSP：`default-src 'self'`；`connect-src` 只允许中继地址；不加载任何第三方脚本；不使用 `unsafe-inline` 和 `unsafe-eval`。
- 构建时把中继地址写进页面；首次设置时把它写进名册，之后以名册为准。
- 每次发布生成资源清单，记录全部文件的哈希，并用发布密钥签名。app 启动时检查清单，不一致就警告。这只能发现 Vercel 被篡改，不能阻止，但可以让用户在解锁之前就知道页面被换了。**[M0：Service Worker 能否可靠地在解锁前完成这项检查]**
- 自动锁定靠页面的输入事件判断是否有人在操作（按键、点击、触摸、滚动），时长设置只保存在这台设备上。

## 10. 踢出、冻结、全部暂停、审计、Node 自保

### 10.1 踢出（关键操作）

1. app 生成新版名册（去掉这台机器），附上断言，**同时**通过中继发给每台机器和大脑，并在 app 里显示每台的确认情况。
2. 这台机器参与的所有域都开启新纪元。
3. 大脑取消它的所有 Run，相关任务回到排队状态。
4. 要求中继断开它的连接（尽力而为，安全不依赖这一步）。
5. 这台机器如果是好的，收到名册后会自己删掉本地的密钥。

### 10.2 冻结和全部暂停（会话签名）

- **冻结**：在名册里标记 `frozen`，各方立刻不再接受它发来的消息，也不再给它下指令。大脑把它的 Run 暂停。可以随时恢复，但解冻是关键操作。
- **全部暂停**：给所有项目自主范围加一个临时的“暂停”标记，大脑停止发起新的工作，暂停正在进行的 Run。恢复只要会话签名。

### 10.3 Node 本地硬规则

只能在本机用 `sous` 命令或编辑 `node.json` 修改，远程改不了：

- 现有的策略底线（`policy`），以及只在工作空间内操作
- 新增：不读取凭据目录（`~/.ssh`、`~/.aws`、`~/.config/gh`、钥匙串、浏览器配置等，可以追加）
- `remote_admin: false` 时拒绝一切远程管理，`shell: false` 时拒绝打开终端，即使附带了断言也不行
- `allow_open: false`（默认）时拒绝 `open` 模式，即使附带了断言也不行
- **自我冻结**：10 分钟内被拒绝的指令达到 3 条，或者收到签名正确但任期过期的大脑指令，就把自己冻结，并上报用户；用户在 app 里确认后解冻（关键操作）

### 10.4 审计

- 每台机器在 `~/.sous/audit.log` 里只追加地记录收到的每条指令：接受还是拒绝、原因、指令哈希，整体串成哈希链。
- 每隔一段时间，机器把日志头 `{seq, hash}` 签名后加密发给用户。app 核对哈希链是否连续，以及机器记录的指令是否都能在大脑的日志里找到对应项；找不到就提醒用户。

## 11. 更新和发布

- **发布密钥**：一对 P-256 签名密钥，私钥只在用户自己的 Mac 上（钥匙串或硬件密钥），不进 CI。公钥编译进 `sous`。
- **流程**：打 tag → CI 构建并发布（和现在一样，darwin 继续用 0026 的证书签名，只为了 TCC）→ 用户在本机运行 `work/scripts/release-sign`：下载 `checksums.txt`，核对，签名，上传 `checksums.txt.sig`，同时给页面的资源清单签名。
- **Node 安装更新**：仓库地址写死在程序里，下载后用编译进来的发布公钥验证 `checksums.txt.sig`，再核对文件哈希。安装更新是关键操作。
- **发布密钥轮换**：新公钥由旧私钥签名，随新版本发布。私钥丢失时，只能让每台机器手动安装新版本。
- CI 被攻破的后果：攻击者能发布带合法 Apple 证书签名的二进制，但没有发布签名，Node 不会安装。

## 12. 中继（sous-relay）

- **接口**：一条 WebSocket，认证方式是名册里的成员对中继发的随机挑战签名（中继只用名册里的公钥做准入，用来防滥用，安全不依赖它）。首次设置时，由用户在中继上执行一次 `sous-relay init` 打印出的一次性令牌来完成绑定。
- **功能**：按接收方的信箱存储和转发（离线时保留 7 天）；按域存放日志和大块数据；广播租约和名册；为配对提供会合点；做健康检查。
- **存储**：SQLite，只存密文和元数据。
- **不再提供**：页面托管、登录、模型调用、联网、推送。

### 恶意中继测试

在 `work/tests/` 里加一个可编程的“恶意中继”，用真实的 `sous` 二进制和页面端的协议代码（通过 Node.js 跑 `src/trust` 的测试）。逐项验证：

| 攻击 | 期望结果 |
|---|---|
| 伪造用户、大脑或 Node 的签名 | 拒绝并记入审计 |
| 重放旧指令、旧的点击批准、旧的断言 | 拒绝 |
| 消息重排、丢弃 | 先缓存，出现缺口时上报 |
| 回滚到旧名册（复活被踢出的机器） | 拒绝 |
| 配对时替换 Node 公钥或身份公钥 | 配对失败 |
| 拿出旧租约，或者伪造任期 | 拒绝；收到过期任期的指令时 Node 自我冻结 |
| 让新大脑拿到落后的日志 | 大脑等待并提示用户 |
| 把一个项目域的密文挪到另一个域，或者挪给另一个接收者 | 解密失败（AAD 不匹配） |
| 用断言签的是 A，实际发送的是指令 B | 拒绝 |
| 关键操作的断言不带 UV 标志，或者 `rp_id`、origin 不对 | 拒绝 |

## 13. 从 0.2.x 迁移

1. 在旧版本上导出：`sous-hub admin backup`。
2. 部署中继和页面，在 app 里完成首次设置（创建身份）。
3. 用新的配对串重新配对每台机器，指定大脑机器。
4. 在大脑机器上运行 `sous brain import <备份文件>`：把旧数据导入本地的 store，按域加密后上传到中继。模型 Key 和 MCP 配置一并迁移。
5. 在服务器上删除旧的 Hub 数据目录和全部备份。**迁移前就留在服务器上的明文副本无法保证已经清除干净**，模型 Key 建议迁移后重新生成。

0.3.0 不兼容 0.2.x 的 Node 协议，各台机器必须一起升级。

## 14. 受影响的决策和契约

- 决策：0002 被 0030 取代；0016（模型存放在 Hub 的数据库里）和 0026（发布的信任根）被 0030 修改；0012、0015、0021 的“需要近期登录”统一改成关键操作。具体写在 0030 里，原记录只改状态。
- 契约：`core-hub-node.md` 和 `core-hub-http.md` 在实现时改写为 `core-relay.md`（中继协议）、`sous-envelope.md`（信封、签名文档、名册、租约，包括规范化编码和测试向量）、`core-brain-rpc.md`（app 和大脑之间的 RPC，由现在的 HTTP 接口演变而来）。
- 文档：`docs/architecture` 加一篇 `trust.md`，在实现完成后编写。

## 15. 对使用方式的影响

| 场景 | 变化 |
|---|---|
| 打开 app | 刷一次 Face ID、指纹或 PIN。iPhone 上 PWA 被系统回收后要再刷一次 |
| 日常聊天、派任务、看进度 | 没有变化 |
| AI 自己干活 | 没有变化；超出项目自主范围时弹一张卡片，点一下就行 |
| 关键操作（§5.3） | 每次刷一次 Face ID |
| 接入新机器 | 在 app 里生成配对串，粘贴到那台机器的终端里 |
| 新手机、新电脑 | 能用同一个同步的 Passkey 就直接可用；不同步的 Passkey 要由已登录的设备添加 |
| 大脑机器全部离线 | AI 停止工作，任务排队；app 只能查看缓存、冻结、踢出、全部暂停 |
| 丢失全部 Passkey | 聊天数据作废，每台机器在本机执行 `sous trust reset` 后重新配对 |
| 发版 | 多一步：在本机签名 |
| 排查问题 | 中继的日志只剩元数据，排查要看大脑机器和 Node 上的日志 |
| 服务器既是中继又是 Node | 这台 Node 不受保护：部署目标最好和中继分开，至少不要把它指定为大脑 |

## 16. 待验证 [M0]

1. WebAuthn PRF 在以下环境的支持情况：iOS Safari（主屏幕 PWA）、macOS Safari 和 Chrome、Windows Chrome 和 Edge（Windows Hello PIN）、Android Chrome，以及通过扫码跨设备认证（hybrid）。不支持 PRF 的平台，退回到“用手机扫码完成跨设备认证”。
2. WebCrypto 的 P-256 不可导出密钥、AES-GCM `unwrapKey`，在 iOS Safari 上的表现。
3. Go 端的 X-Wing、HPKE 实现（标准库或 x/crypto 当前提供了哪些），浏览器端 ML-KEM 库的审计状态，两边能否用同一套测试向量互通。
4. Go 访问 Secure Enclave 和 TPM 的方式，以及这对“不用 cgo 的交叉编译”有什么影响。
5. Service Worker 能否在解锁之前完成资源清单的检查（§9）。
6. Chrome DevTools 的虚拟认证器是否支持 PRF，用于端到端测试。
7. 从国内访问 Vercel 自定义域名的速度。

## 17. 实现说明（0.3.0-alpha1 实际做法，和上文不同的地方）

M0 的结论和实现时的取舍。已经在这里写明的，以这里为准。

| 设计 | 实际 | 原因 |
|---|---|---|
| §2 X-Wing 有待确认 | Go 用 1.26 标准库 `crypto/hpke` 的 `MLKEM768X25519`；浏览器用 `@noble/post-quantum` 的 `ml_kem768_x25519`，HPKE 的密钥调度是自己按 RFC 9180 写的。两边的向量互相验证通过 | noble-post-quantum 只经过作者自审；混合方案下 X25519 那一半仍然有效 |
| §3.3 密钥放进硬件 | 软件密钥（`trust/keys.json`，权限 0600），名册和页面上标注为“软件密钥” | Go 访问 Secure Enclave 或 TPM 需要开 cgo，会破坏现在不用 cgo 的交叉编译；留到以后 |
| §4 配对还有二维码方向 | 只做了“页面生成配对串，复制到机器上”这一种 | 已经满足要求；二维码留到以后 |
| §5.2 “点一下”的批准卡片 | 机器拒绝时，错误以“超出自主范围：”开头；Run 卡片上的“许可并重试”发一个 `run` 许可（按 `task_id`，不需要 Face ID，5 分钟内有效一次），然后重新派发 | 范围外的事很少，先保证安全上正确 |
| §5.3 打开终端由机器核对 | 打开终端、安装/登录/退出 agent、写 API Key、写配置、修改角色或工作空间、更新、解冻，都是“许可 + 断言”，由机器核对；模型供应商和 MCP 是“意图 + 断言”，由大脑核对 | 和 §5.3 一致，补充写清楚 |
| §7.2 普通机器用域的公钥加密写入 | 机器的输出直接在加密通道里发给当前大脑，效果同样是“只写不读”（普通机器不持有任何数据密钥） | 更简单；大脑换人时，发件箱会重发到新大脑 |
| §7.3 事件日志按域加密复制 | 整个 Hub 数据目录打成 tar.gz 快照，按 4 MB 分块加密上传，两个槽位交替，清单由持有租约的大脑签名；只有一个数据域 | Hub 的存储不完全是事件溯源，快照最可靠；代价是故障切换时最多丢最近一分钟，不能按项目排除大脑 |
| §8.5 本地缓存 | 没有离线缓存：大脑全部离线时，页面只显示机器管理和全部暂停 | — |
| §9 资源清单签名 | 没有做；`vercel.json` 带严格 CSP，只从本机部署 | Service Worker 没法在解锁前可靠地检查清单 |
| §10.3 凭据目录黑名单、`shell: false` | 沿用已有的 `remote_shell`、`remote_admin` 和策略里的敏感读取规则；新增 `allow_open`（默认允许，作为本机否决）。自我冻结的条件是 10 分钟内 3 次越权 | — |
| §12 恶意中继测试放在 `work/tests/` | 放在 `apps/core/internal/brain/adversary_test.go`，用中继的 `Tap`、`Inject`、`InjectDoc` 钩子 | 要用到 internal 包 |
| §13 迁移 | `sous brain import`，把这台机器的快照计数设成当前时间，让导入的数据胜出 | — |
