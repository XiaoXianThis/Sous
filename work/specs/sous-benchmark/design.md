# Sous Agent Benchmark：实施设计

本篇保留全产品诊断和远期工程设计。**已实现的主管能力及版本对照以 [runner 文档](../../tests/e2e/sous-bench/README.md) 和 [主管能力主评测](supervisor-evaluation.md) 为准**：严格成功率作为主分，成本、自主性和时效单列。下文示例 CLI 和全链综合分不是当前实现，也不作为首轮交付物或版本提升证据。

## 1. 三条轨道，各自出结果

| 轨道 | 固定/替换什么 | 从哪里发起 | 回答什么问题 |
|---|---|---|---|
| `offline` 系统基线 | 真实 Hub、Node、Git、SQLite；独立脚本模型和 ACP agent，固定流延迟与故障点，不出网；功能与负载用不同 profile | HTTP/WS + CLI；也可从消息进入 | 协议、状态、恢复和审批有无回归？同一负载下 Sous 本体开销变了吗？ |
| `role` 单阶段 | 一次只保留一个真实可变组件：例如真实主管配脚本 worker；或固定任务直接派给真实 worker；验收/审批用固定产物/审批请求、标注结论 | 主管走消息、执行走任务 dispatch；审批和验收走产品实际状态机 | 是谁理解错、路由错、产物错，还是审错了？ |
| `live` 产品端到端 | 所有配置角色和执行 agent 用真实连接；本地合成项目、固定用户脚本和独立判题 | `POST /threads/{id}/messages` 或用户实际入口；不得替主管补任务参数 | 用户请求到最终交付有多可靠？需等多久、花多少钱、被打扰几次？ |

另设 `live-connector` 和 PWA 冒烟，分别出覆盖率，不混入主分。工作机离线等真实轨故障可控地注入，外部服务故障不和可控故障用例混算。离线用脚本状态机响应请求而非逐字匹配历史录包，检查协议和必要因果约束；主管路径变化时用通用行为脚本继续，无法覆盖的新行为标记夹具不兼容并另修，在此之前不作可比结论。

## 2. 实验矩阵：分离 Sous、模型和执行 agent

每个实验固定并快照：Hub/Node 二进制哈希及 commit、初始数据和 prompt/夹具版本、全部角色**解析继承后的**配置、供应商协议/API 路径、模型标识及可得的实际回复模型、effort/窗口/采样参数（未暴露则记录未知）、Node 版本/槽位/策略、ACP 适配器和 agent 版本、执行 agent 的模型与选项、OS/架构/机器规格/网络、并发、超时、缓存场景、种子和 judge 版本。实际模型/选项无法确认时标 `unverified`，不宣称结果归因到某个具体模型；模型别名漂移时标记不同批次，不静默合并。相同 effort 标签不视为跨供应商等计算量。

| 对照 | A → B 的唯一变动 | 怎么解释 |
|---|---|---|
| Sous 版本 | 只换 `sous-hub` / `sous` 构建 | 先跑离线，再跑匹配真模型；提示词作为 Sous 版本的一部分，若要归因到提示词则单测它 |
| 主管模型 | 只换 `supervisor` 的 provider/model 配置 | `reviewer/approver/inspector/compactor` 全部显式钉住，避免隐式继承一起换。跨协议结果归因到接入配置整体，不冒充纯模型差异 |
| 执行 agent/模型 | 固定 Sous/主管和同一任务契约，先只换同适配器内的模型，再另测适配器 | 若适配器不能固定或报告其模型，结论只针对整套执行栈 |
| 审批/验收/整理 | 一次只动相应角色或一项策略，先跑阶段题再上全链 | 典型度量分别是人工升级＋误放行、误收/误拒、跨整理约束保持＋上下文 token 增量 |
| 交互作用（按需） | 两个主管 × 两个 worker，共 4 格；同模型 effort 另做独立扫档 | 仅对入围配置做，不跑无意义的全排列。对比组合收益及前沿，不泛化到未测配置 |

按 `场景/变体/重复编号` 做配对，块内以固定种子打乱 `AB`/`BA` 顺序，匹配时段、机器配额和负载；真实模型 seed 只在 API 明确支持时启用，不承诺确定性。先做 `A/A`：两份同配置独立运行，测波动和量测误差。冷（新 DB、进程、会话；上游缓存状态若不可控标未知）和暖（可复用前缀、会话/连接，按脚本预热）分开；不让 B 免费吃 A 的预热。换 provider 和 effort 的选型优先交付阈值相同，再看耗时/实际成本的 Pareto 前沿。

## 3. 自动判题与计分

### 判据顺序

1. **硬门禁**：不允许的副作用、未授权执行、越项目改动、伪报已交付（与可验证证据矛盾）、重复交付等按题的强制不变量验证。任何已观察到的硬失败触发 `FAIL`，绝不被其它分抵消。无证据证明门禁被执行则 `INCOMPLETE`，不是默认通过；同时有硬失败和数据不全时仍报 `FAIL`，并标数据不全。
2. **确定性 oracle**：独立脚本比对文件/结构化数据、Git refs 和提交树、测试退出码、HTTP/WS 可观察状态、工具 side-effect 账本。检查必要事件的因果顺序而非逐字快照；必须检查**不该发生**的动作，并在同题终止后固定观察窗内核对晚到的副作用。任务标记 `done` 只是证据之一。断言分别标 `required` 或 `diagnostic`。用已知正确、空输出、误改文件、误报成功等变体验证 oracle 的正反例；基线 fixture 自检失败即 `harness_invalid`。
3. **文本打分**：优先把事实、约束、测试状态和不确定性映射成枚举或可核验 claim，同义表述不扣分。只对确实无法规则化的沟通质量启用独立 `judge`：冻结模型/提示词/分项 rubrics，隐藏被测模型标识，给裁判合成参考证据，不给裁判工具，输出结构化事实依据与理由。首发主分**不包含** judge；它另出辅助分。用人工标注的锚定样本覆盖合格/不合格，先验一致性再启用（例如二分类 κ ≥ 0.7，分歧与边界样本复核）；发现漂移则停发辅助分。日常只抽检分歧、边界和新增题。产品自身 reviewer 是被测件，不能当裁判。

### 一次尝试与可选的产品综合分

- `P` = 1：在 deadline 前达到题面允许的终局（包含正确澄清、正确拒绝/等待），所有 required 断言和硬不变量为真；否则 0。`partial` 为通过的诊断断言比例，只辅助定位，不救活失败任务。系统超时、代理拒绝合规任务、可复现连接器错误、任务跑完却没产物均计失败。
- 只对 `P=1` 计自主性 `A = max(0, 1 - 0.25 × extra)`；`extra` 是超过用户脚本预先登记的可接受次数/类别的干预，审批、问题、验收分别记账，重复按语义/请求身份合并，但重复向用户索要另计。**必要的澄清和审批不扣分**；消失的必要审批会让 `P=0`。报告同时给零额外干预交付率与总干预次数（不等同于全自治）。
- 只对 `P=1` 计时效 `L = clamp((deadline - elapsed) / (deadline - target), 0, 1)`。`elapsed` 从发起任务到满足终局和产物可用；含任务内脚本用户等待，不含环境预热、判题和收尾；报告另拆人等/系统等。每个 profile 中每题有固定 `target < deadline`，用基线 pilot 和产品需求设定再冻结；不拿当次最慢样本做归一化。不提前停止以骗分。
- 若将来需要综合分，可校准原方案 `S = 80 × P + 10 × P × A + 10 × P × L`：按重复、变体、场景及域聚合；这组数**没有实测依据，不发布为主分**。先直接发布严格通过率和门禁，额外干预、耗时、费用及样本覆盖单列。若合理改变权重即可逆转结论，不使用综合分排名。
- 首版用例 deadline 可从对话 60s、小型执行 300s、多阶段执行 600s 起步；这些是 pilot 起始预算，不是已测出的 SLA。负载轨使用独立计时门槛，不能把 mock 加速的比例套到真实链路。

`product_failure` 与 `harness_invalid` 分开：runner 本身崩溃、夹具预检失败、oracle 失联导致无法裁判是无效，不是通过也不是产品失败。正式比较要求所有计划题/配对都得到有效结果，缺题不重分配权重；预先登记的无效替补允许同区块两臂重排最多一次，完整保留无效记录。供应商 429/5xx、断流或 adapter 额度失效在 `live` 默认计用户可感知失败，并单独归因；系统对照可以附加发布“双方上游均可用”的敏感性视图，但不替换主结果。预算用尽未发起的尝试标 `not_run`，批次 `INCOMPLETE`。不把“重跑一次成功”替换掉第一次失败；产品自己的重试保留在同一尝试内并计成本。

## 4. 指标采集和缺口

| 指标组 | 计算/口径 | 现有采集点与限制 |
|---|---|---|
| 任务与沟通 | 严格交付率、首轮交付率、各域通过率、工具/回合/返工/审批计数、升级率、错误归因；每题连续 `k` 次全通过的比例（固定非重叠重复组）另报，不能用挑最好一次的 pass@k | `/ws?since=` + `/tasks/{id}`、`/talk`、`/runs/{id}`、`/log`、`/diff`、`/approvals`，再与独立 artifact 对照。按 `thread_id/topic_id/task_id/run_id`、事件 `seq` 和工具调用 ID 去重；日志、文案只作辅助证据 |
| 用户时延 | 首个可见文本 TTFT（不含 thinking），接收到派发、排队、worker 运行、审批往返、验收返工、最终交付的 P50/P95；超时率单列 | WS **发送前**开始订阅；以 runner 单调时钟记请求发起与接收。持久事件可重放，丢失的 `seq=0` 流式数据不能补；TTFT 标 `missing`，不能拿最后一条消息时间充当。重放帧不能用重放到达时间计算实时延迟。跨机分段用同一采集时钟的观测点或标未知，不直接减未同步的墙钟 |
| 稳定与恢复 | 从注入到检测/恢复、最终恢复率、遗漏/重复次数、会话和进度保留、断开后的 outbox 排空 | `run.paused/resumed/ended`、状态快照、IPC `status` + 独立 append-only 账本。通过测试代理或 runner 控制子进程在指定检查点断开，不按固定 sleep 猜执行进度 |
| 用量与效率 | 按角色/模型的 input/output/cache-read/可得的 cache-write/reasoning；请求数、重试、每成功任务耗时、每成功任务费用、成功任务每分钟、有用改动与额外动作 | Hub `/usage` 是聚合；逐次优先用本地评测实例可见的 `usage.recorded`（先验明可见性，必要时用一致备份的只读版本化 reader），包含实际模型、角色及关联字段。角色调用数不等价于供应商网络尝试数。受控 provider proxy 可补请求起止、状态码、重试、原始计费字段；只保留脱敏结构化元数据，禁止保存认证头、请求体或流明文。无法逐题关联的并发请求只作批次聚合 |
| 执行 agent 成本 | `worker_usage_source = gateway | vendor_export | unavailable`；按可关联请求/尝试报覆盖率 | 当前 `ACP`/Hub 没有通用的 worker 账单接口。用明确支持计量的适配器/专用项目账单补齐；闭源订阅和缺字段明确 `unknown`，绝不按 0 元。官方价表快照固定币种、版本和日期，区分冷输入/读缓存/写缓存/输出价格。不能从 cache-read 算出 cache-write；Hub 汇总可能没有这个字段 |
| 性能与容量 | 墙钟（含失败）/成功数、峰值 RSS、每成功任务 CPU 秒、峰值子进程数、SQLite 文件/WAL 增长、吞吐/错误/积压；持久化延迟与断开重连 | 同一 OS/机器规格对照；Linux 用隔离进程组或 cgroup 采 Hub/Node/worker，按层标覆盖，其他平台用等价指标或 `N/A`。系统图是内存滚动诊断，不是完整 trace。没有可靠的纯 Sous CPU 或中间段计时就分别报可观测层，不用总墙钟减 provider 时间推算（会并行重叠） |

定义：`每成功任务费用 = 批内所有尝试实际可核算费用 / 严格成功数`（包括失败和重试；成功为 0 时不可计算，单列批次总支出）。Hub-only、worker-only、all-in 分开显示；前两项覆盖均完整才发布 all-in，否则标不可用，若用估计价另列 `estimated`。预热和 judge 成本不计入产品尝试费用，但计入评测实际预算。成功任务墙钟/成功数亦显式区分单并发累加时长与并发批次吞吐。预算预检根据调用/时间/输出上限与价表预留并发在途额度，超阈停止发新单；异步账单无法保证硬美元上限，真模型仍须专用供应商项目限额或可执行的代理调用硬限制兜底。

**性能 profile**：先做并发 `1/2/4/8` 的固定时长阶梯，固定 Node 槽位/数量，记录端到端吞吐与排队；再用固定到达率发请求，延迟从计划到达记起，报完成、积压、超时与压测机丢单，不让发压端自动等上一个完成掩盖过载。短场景 warm/cold 分开采，默认每格 ≥100 个有效延迟样本再出 P95；成功条件延迟与超时比例一起报。稳定档加固定时长 soak（如 30 分钟）验证队列不持续堆积、结束后无遗留进程和无重复副作用。真实负载另测且受预算约束，不能用其混杂上游的结果作 Sous 本体性能门禁。

## 5. Runner 工程与隔离

拟建 `work/tests/e2e/sous-bench/` 独立 Bun/TypeScript 工具项目。只调用构建产物和已有契约，不 import `apps/core/internal`，不读取生产库。功能模块文件放项目直属或一个子目录层级 (`runner/`、`drivers/`、`oracles/`、`cases/`、`profiles/`)；共享合成 fixture 放 `work/tests/fixtures/sous-bench/`。依赖在 helper 目录安装；Go 构建仍由 core 的已有 build task 负责，runner 不在根目录执行安装、构建或编译 app。

1. **`doctor` / 隔离**：传入两套或一套 `sous-hub`/`sous` 路径（默认 `build/core`），检查二进制、Git、端口、能力、凭据和网络限制。每次尝试分配独立或恢复自干净快照的 DB、配置、`SOUS_HOME`/`--home`、临时 HOME、项目、分支和本地 origin。实际执行在独立低权限容器/VM；测试目录隔离不是沙箱。只挂合成项目和相应二进制，oracle 与答案在 agent 不可读写的独立边界；不继承宿主 HOME、SSH agent、Git 全局配置、真实 repo、系统密钥链。离线档禁外网；真实档只允许明确的供应商出口，凭据与受测执行环境分离，无法收敛出口或凭据权限的适配器不进入无人值守档。默认关闭远程 shell/admin、自动 fetch 和非必要对外连接器，不降低产品已有审批/隔离限制。角色、MCP 和测试审批的选择来自夹具而不是受测输出。
2. **启动**：用生成的 `hub.yaml` 回环监听、独立 `data_dir`、`dev: true`（**仅本地测试**）。等 `/healthz`；`POST /auth/dev-login` 维护会话 Cookie 和 `X-CSRF-Token`，用 `POST /nodes/pairing-code` + `sous pair ... --home ... --workspace ...` 注册；准备 `node.json` 的 `custom_agents`（脚本 ACP），或预置真实适配器；启动 `sous daemon`，通过 `/nodes` 等在线/agent 就绪。每批用空 DB 从 YAML 初始化角色，再用 `/models` 核对有效角色；非首次启动不假设 YAML 会覆盖 DB。故障用例保留其沙箱 DB/工作区重启。
3. **执行**：监听 WS → 建 thread/project → 应用 fixture → 通过消息/任务入口开始计时 → 按 checkpoint 驱动用户/故障脚本 → 采终局、抓快照并校验。脚本只回应标注的澄清和审批，未知请求判 `unexpected_intervention` 或按题定义转失败，不自动批准。每题固定 timeout；取消与清理强制执行，不把进程污染到下一题。
4. **产物**：`work/logs/sous-bench/<run-id>/` 存 `manifest.json`、`attempts.ndjson`、`summary.json`、`report.md` 和脱敏 evidence；临时实例在 `work/tmp/sous-bench/<run-id>/`，结束清理；可再生数据放 `work/cache/sous-bench/`。不上传整个 DB、环境文件或原始流；使用权限受限的输出目录。需要长期比较时把脱敏报表交给 CI artifact 存储，按 run-id/构建/suite/hash 索引。

**case manifest 示例**（工程实现用 JSON Schema 校验；以下仅示意）：

```json
{
  "id": "patch-regression.v1", "domain": "delivery", "tier": "core",
  "profiles": ["role-worker", "live"], "fixture": "calendar-boundary.v1",
  "entry_by_profile": {"role-worker": "task-dispatch", "live": "chat"},
  "target_ms": 120000, "deadline_ms": 300000,
  "user_script": "no-follow-up.v1", "fault_plan": "none",
  "required": ["fix-tests-green", "baseline-tests-green", "report-matches-artifact"],
  "hard": ["allowed-paths-only", "no-main-change"],
  "diagnostic": ["planning-actions", "first-run-pass", "unexpected-interventions"]
}
```

`attempt` 至少记 `run_id/arm/case_id/variant_id/repeat/seed`、终局与测量状态、每条断言的期望/实际/证据引用、阶段计时及有效性、`thread_id/topic_id/task_ids/run_ids`、资源/用量/计费来源、`first_failure_stage` 和 `reason_code`。`manifest` 固定实验与评分版本、所有已计划样本和产物哈希；`summary` 含分域分/置信区间、覆盖率、门禁、两臂差值、性能和效率账本。因果不明确时标 `unattributed`，而非硬猜模型原因。

预期接口（**尚未实现**，在 `work/tests/e2e/sous-bench/` 执行）：

```sh
bun run bench doctor --profile offline
bun run bench run --profile offline --suite smoke
bun run bench matrix --profile live --matrix supervisor-ab --repeats 3 --max-usd 25
bun run bench compare --base <run-id-a> --candidate <run-id-b>
bun run bench report --run <run-id>
```

退出码：`0` = 已完成且门禁通过（pilot 可无质量门槛但不能无硬门禁）；`1` = 检出阻断回归/硬失败；`2` = 配置/夹具无效、缺题或对照不可比。非零也写报告；比较时验证实验签名，只允许声明变量与实现固有差异。

## 6. 基线、门禁、优化闭环

| 时机 | 规模与结论 |
|---|---|
| PR | 12 个离线冒烟起步，全部 required 通过、零硬失败；改动命中相关模块则跑对应扩展集。无需付费账号 |
| 夜间 / 按预算手动触发 | 真实 8 题 × 3 次/配置做 pilot；正式库扩到 36–60 场景，每域至少 4 个独立场景，有握手失败、否定需求和噪声等变体。以 3 次/题起步，不确定的结论通过加样或扩大题集解决，不许用重复一题代替场景覆盖 |
| 发布 / 模型切换 | 正式套件＋压力和恢复对照；两臂同窗口交错，正式集按题族分层抽取，主张可靠性前增加到 5 次或按 A/A 波动与最小有意义差值算额外样本。保留不反复调参的 holdout（例如 20% 的独立场景族），冻结题库、模型和价表再跑 |

报告最小可检测差、实际有效样本数、每个分数的 95% 区间。固定题库使用按域、场景聚类的配对 bootstrap（同 case 的重复一并重采、基线与候选同时取），用于题库对照的误差提示，不把相关变体当独立证据，也不把题库外推到真实用户总体。`A/A` 或样本过少时只给趋势。建议初始门槛：硬不变量零容忍；质量用严格通过率差的配对区间，95% 下界至少 `-2pp` 才能宣布非劣，上界低于 `-2pp` 判回归，跨线判不确定，样本不足补测；核心域任何显著退化单列，不能被总分隐藏。性能在同机可控负载下，P95 或 CPU/成功初始回归阈值 `+10%`，先过 A/A 噪音检验并用复跑确认，再升为发布门禁。阈值在基线建立后预先冻结并版本化，不随候选结果改。

报告按严重性列 `expected → observed → evidence → first_failure_stage` 和复跑命令，同时输出两臂原始分项与变化。例：任务正确但审批转人工变多，先看 `approval.reason` 和用量，而不是换 worker；产物正确但多次返工，核查 reviewer 的误拒；仅真模型尾延迟变大、离线压力持平且 provider 等待同时上升，优先排查模型链路。每次迭代保留基线、单改一项、复测受影响题族和全链抽样；连续几次失败的新类型固化为 oracle 或新题，不在报告里手改分数。
