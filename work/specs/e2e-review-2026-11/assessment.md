## 三、更好或应补做的做法（按优先级）

1. **回合结果分类（合并 4.1 和 4.14）**：在 Node 里统一分类，以结构化信号为主，“0 次工具调用 + 命中额度文本”作为兜底；`RunEnded` 增加 `error_kind`。成本约为 Node 一处、Hub 一处、加测试（假 agent 增加一个“只回一句 Upgrade your plan 就 end_turn”的模式）。
2. **把拒绝信息带上来（4.2）**：`RunEnded` 带上 `refused`；“有用户拒绝 + 验收不通过”时直接 `blocked`；`userPrecedent` 覆盖人工审批。比“拒绝即结束 Run”改得少，也保留了“换个办法”。
3. **部署和代码任务建立父子关系（4.5、4.1）**：自动部署传 `ParentID`；阶段条只看子任务；ops 成功后由 Hub 触发一次健康检查，失败就 `blocked`。
4. **只有 deliver 不计并发（4.3）**：Hub 的 `Busy` 和 Node 的 `sem` 都跳过 deliver；rebase 保持计数。
5. **修正任务行的 agent 回退顺序（4.4）**：`agent_pref` 放到岗位前面，排除 `sous`；然后再加 `last_run_agent`。
6. **构建新鲜度检查（4.23）**：先做这一项，再复测 4.18、4.8、4.25，避免修了不存在的问题。
7. **空 diff + 验收不通过直接 blocked**，替代“空 diff 一律判失败”。

## 四、报告遗漏的问题（按严重性排序）

1. **【高】等待用户审批的 Run 一直占着机器工位。** `node/run.go:125` 在整个 Run 期间都持有 `sem`，审批可能等上几个小时；Hub 的 `Busy` 也把它算作 running。在“一人多项目”场景下，两张没处理的审批卡就能让一台机器停摆，4.3 的交付排队就是这样触发的。建议：等审批时让出 Hub 侧的计数，或者给每台机器的并发增加“等审批不计”的口径；最低限度也要在 UI 上说明“被审批占用”。
2. **【高】自动部署会被无关或失败的 ops 任务压掉。** `task/workbench.go:574` 用 `DeployedSince` 判断“已经部署过”，条件只是“项目里在 PR 任务之后创建了一个没取消的 ops 任务”（`workbench.go:591-595`）。PR 合并之前如果跑过一次巡检、清理日志，或者上一次部署**失败**了，合并后的自动部署就不会触发，而且没有任何提示。修法和第三节第 3 条相同：用 `ParentID` 关联。
3. **【中】自动部署在创建失败时永远不会重试。** `workbench.go:572` 先 `SetSetting(key, "MERGED")`，再在 `:577` 调用 `Create`；`Create` 失败只打一条 warn（`:582`），下次轮询看到 key 已存在就跳过。应该在 `Create` 成功后再写 key。
4. **【中】被拒绝的信息在 `end_turn` 路径上丢失。** 见 4.2 第②(b) 点（`run.go:354-386`）。除了导致重试，reviewer 的提示（`advance.go:246-249`）也看不到“用户拒绝了什么”，会把“尊重用户的拒绝”误判成“没干活”。
5. **【中】人工审批模式下没有去重。** `approve.go:45` 让 `userPrecedent` 只对 AI 审批生效。这是 4.2 的直接成因，报告把它当成需要新建的功能，其实只要扩大已有规则的适用范围。
6. **【低】交付期间任务行显示的 agent 是 `sous`。** `TaskRow.tsx:16` 取当前 Run 的 agent，交付 Run 的 agent 固定是 `sous`（`engine.go:620`）。
7. **【低】报告本身的方法问题。** 被测的 Hub 托管着旧的 web 构建（报告 4.23），但报告没有标出哪些前端发现是在旧包上得到的；4.18 在当前源码里不成立，4.8 用报告引用的命令无法复现。建议以后的报告在每条发现旁边记下“构建 commit”，并附上审批的原始 `RawInput`。
