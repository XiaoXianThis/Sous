# sous MVP：需求

第一期目标：跑通核心闭环。**指挥 → 干活 → 审批 → 汇报 → 通知 → 反馈**，并且能自主、长期运行。

用户只有一个人（作者本人）。界面只做中文。

## 范围

| 第一期（本 spec） | 第二期及以后 |
|---|---|
| PWA 对话、任务、审批、机器、设置 | 桌面窗口和托盘（apps/desktop） |
| `sous` 命令行：daemon、配对、状态、终端聊天 | 会议旁听模式 |
| 5 个子 agent：Claude Code、Codex、Kiro、Cursor、OpenCode | 操作电脑，带主动避让 |
| 三种模型接口格式，默认 DeepSeek | Telegram、飞书等更多入口 |
| Web Push 通知 | 向量记忆 |
| 进程看门狗 + 巡检 agent | 花费上限 |
| 手动更新 | 操作系统级沙盒（真正的执行隔离） |
| | 从长段对话或会议转写中自动提炼任务（extractor） |

## 需求

### R1 对话

1. 用户可以在 PWA 里和主管 agent 对话；回复以流式输出。
2. 对话按线程（Thread）组织；所有线程共享同一个助理身份和同一份记忆。
3. 换设备打开时，能看到完整的历史，并从上次中断的地方继续。
4. 用户可以在 `sous chat` 终端界面里对话，效果与 PWA 相同。
5. 有一条固定的**主线**线程：系统事件、主动汇报、巡检发现的问题都发到这里；打开 PWA 时默认进入主线。由某个线程发起的任务，其后续事件和汇报回到发起它的那个线程。
6. 遵循“最少注意力”原则：接到任务确认一次，执行期间保持安静；只有出了结果、需要用户决定、或者做不下去时才主动发言；一次只问一个具体问题。

### R2 任务

1. 主管 agent 在对话中自行创建和维护任务（通过任务工具），用户在界面上能看到、修改、取消任务。第一期不单独设置 extractor。
2. 任务状态：`inbox → planned → running → waiting_approval / blocked → review → done / failed / cancelled`。
3. 任务可以拆分成子任务，也可以设置依赖关系。
4. 每个任务可以有多次执行（Run），失败后可以重试，或者换一个 agent、换一台机器再做。
5. 任务完成后，由 reviewer 验收；验收时能看到完整的 diff（过大时截断，并附上文件列表）。验收不通过就打回重做，并记录原因。
6. 任务分两类：**代码任务**在项目的 git worktree 里执行；**一般任务**（不涉及仓库，比如查磁盘占用）在临时目录里执行。
7. 代码任务验收通过后，默认 push 分支并创建 PR（这一步按权限模式审批）。**sous 永远不直接合并到主分支**，由用户自己合并。出现冲突时，主管派一个新的 Run 去 rebase。
8. 工作期间线程里的后续消息，直接作为上下文送给正在执行的任务。

### R3 调度子 agent

1. 支持通过 ACP 驱动 Claude Code、Codex、Kiro、Cursor、OpenCode。
2. 每个 Run 在单独的 git worktree 里执行。
3. 子 agent 的进度、工具调用、输出都实时显示在界面上。
4. 子 agent 发起的权限请求，按权限模式处理（见 R5）。
5. 用户可以随时暂停、终止某个 Run，或者在执行中途追加指令。

### R4 机器与路由

1. 每台电脑运行 `sous daemon`，通过一次性配对码接入 Hub，配对后可以在界面上改名或吊销。
2. 每台机器向 Hub 上报：在线状态、操作系统、已安装的 agent 及版本，以及每个 agent 的**登录状态**。没登录的 agent 不参与路由，界面上会提示去登录。
3. 用户在界面上登记项目：名字、所在机器和路径，以及**机器优先级列表**。
4. 任务路由有三种方式：在对话里主动指定；在界面上手动选择；按项目的优先级列表，自动选第一台在线并且装了所需 agent 的机器。
5. 没有可用机器时，任务进入排队状态，并通知用户。

### R5 权限与审批

1. 三档权限模式：默认、自动审批、完全开放（定义见 docs/decisions/0005）。可以设置全局默认值，再按项目或按任务覆盖。
2. 底线规则在任何模式下都会拒绝匹配的操作；底线在 Node 本地配置，用户可以关闭。
3. 待审批的操作会推送通知；用户可以批准、拒绝，或者修改后批准，并可以附上一句话说明。
4. 权限规则由 Node 在本地再校验一遍，不完全依赖 Hub 的判断。
5. 每次审批（无论人工还是自动）都写入事件日志。
6. 在默认和自动审批模式下，子 agent 必须以“每个操作都询问”的方式启动，让所有操作都经过 sous 的权限判断；只有在完全开放模式下，才允许子 agent 按它自己的规则放行。
7. 权限模式和底线规则是**安全网，不是安全隔离**：底线规则按命令文本匹配，可以被换个写法绕过。真正的隔离要靠操作系统级沙盒，放到第二期（见 docs/decisions/0010）。
8. 来自外部的内容（网页、文件、子 agent 的输出）一律只当作数据，不能改变权限或触发审批放行。

### R6 汇报与通知

1. 通过 Web Push 通知用户，包括：需要审批、任务完成、任务失败、任务受阻、巡检发现的问题、主管主动汇报。
2. 通知可以按类型开关，并可以设置免打扰时段（免打扰期间只推送审批类通知）。
3. 点开通知直接跳到对应的任务或审批页面。

### R7 自主运行

1. 支持定时触发：用户可以通过对话或界面创建定时任务（比如每天早上汇总进展）。
2. 主管 agent 会主动跟进：受阻的任务、超时的 Run、等待用户回复的问题。
3. 进程看门狗：Hub 和 daemon 崩溃后自动重启，并从事件日志恢复，正在进行的任务能续上。
4. 巡检 agent 定时巡检（默认每 10 分钟），发现运行过久、陷入循环、token 消耗异常时，按严重程度暂停、终止或通知。
5. 每次模型调用都记录 token 用量，界面上能看到。

### R8 记忆

1. 主管 agent 能记住用户的偏好、项目知识、经验教训，并在之后的对话里检索使用。
2. 用户可以在界面上查看、修改、删除记忆。

### R9 模型配置

1. 支持三种接口格式：OpenAI Responses、OpenAI Chat Completions、Anthropic Messages。
2. 每个 provider 可以配置 `base_url`、`api_key`、模型名；API key 只从环境变量或 Hub 本地的密钥文件读取，不能通过界面回显。
3. 按角色分配模型：supervisor、reviewer、approver（自动审批）、inspector。默认全部使用 DeepSeek。

### R10 部署、安全与更新

1. Hub 部署在 `https://agent.wxian.cc`，只有一个用户，用 Passkey 登录。Passkey 丢失时，可以在服务器上执行 `sous-hub admin passkey-reset`，生成一个新的一次性注册链接。
2. Hub 不执行 shell 命令，不读写代码（见 docs/decisions/0002）。
3. Node 主动连接 Hub，电脑上不开放入站端口。
4. `sous` 能在 Windows、macOS、Linux 上注册成系统服务。
5. GitHub Actions 在打 tag 时构建三个平台的产物并发布到 Releases；界面上手动点击更新。
6. 提供 SQLite 备份脚本，用 `VACUUM INTO` 生成一致的快照。

## 验收场景

1. **核心闭环**：在手机上说“给项目 X 加一个 Y 功能” → 主管创建任务，并按优先级选中 Mac → Claude Code 在 worktree 里开发 → 要 push 时手机收到审批推送 → 批准 → reviewer 看过 diff 后验收通过 → 审批后 push 并创建 PR → 主线里收到完成汇报，里面有改动摘要和 PR 链接。
2. **跨端继续**：在手机上开始的对话，到电脑浏览器和 `sous chat` 里都能继续。
3. **离线排队**：Mac 合盖期间布置的任务进入排队；Mac 开机后自动开始执行。
4. **崩溃恢复**：执行中途强杀 daemon，它被自动拉起后，任务能续上或者被正确地标记为失败，并且通知用户。
5. **巡检**：人为制造一个反复调用同一个工具的 Run，巡检 agent 在一个周期内发现并暂停它，然后通知用户。
6. **换 agent**：同一个任务分别交给 5 个 agent 中的任意一个，都能完成。
