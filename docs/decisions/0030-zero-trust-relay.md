# 0030 零信任：服务器只当盲中继，Node 只认用户的签名

- Status: Accepted
- Date: 2026-11-12

## Context

0.2.x 的 Hub 是完全可信的：它验证登录、运行主管、保存全部数据和模型 Key，并直接给 Node 下指令。Hub 一旦被攻破，攻击者就能在所有机器上执行任意代码、读取全部数据，还能借 `node.update` 的 `repo` 字段让所有机器安装任意二进制。2FA 和 Passkey 登录防不住这种情况：验证是 Hub 自己做的，Hub 被攻破，验证就可以被跳过。

目标：服务器被攻破、拿到 root 甚至全部源码，也无法控制任何一台机器，也读不到任何数据。

## Decision

1. **Hub 改成中继**（`sous-relay`）：只转发和存放密文，不持有任何密钥。主管等“思考”的部分搬到用户指定的大脑机器上（见 0031）。取代 0002。
2. **信任根是用户的 Passkey**：用 PRF 扩展包装身份密钥。启动 app 时解锁一次，得到不可导出的会话密钥；自动锁定时间在 1 分钟到“永不”之间可调，默认 15 分钟。没有主密码，不设恢复码；Passkey 全部丢失时聊天数据作废，Node 在本机重新配对。
3. **Node 只执行签过名的指令**，自己验证：名册、任期、序号和哈希链、过期时间。授权分三档：范围内的由大脑签；范围外的要用户在 app 里点一下（会话签名）；关键操作要用户刷 Face ID，并且由 Node 或大脑自己核对这次 WebAuthn 断言。收紧权限的操作（冻结、全部暂停、取消）只要会话签名。
4. **配对用高熵配对串**：由用户自己从 app 搬到机器的终端（或者扫二维码），内含身份公钥指纹和 128 位一次性秘密，不经过中继。
5. **端到端加密**：数据按主域、项目域分别加密，按纪元轮换密钥。普通 Node 不是任何域的成员，只拿到公钥用来写入（只写不读）。签名用 P-256，密钥封装用 X-Wing（X25519 + ML-KEM-768），对称加密用 AES-256-GCM。只用标准算法和经过审计的库。**项目文件不加密。**
6. **发布签名用离线密钥**：Node 只安装签过名的版本，仓库地址写死，安装更新是关键操作。0026 的 Apple 证书继续留在 CI，只用来保住 TCC 授权。
7. **页面托管在 Vercel**，用用户自己的域名，只从本机部署，严格 CSP，资源清单签名。
8. 0012、0015、0016、0021 里“需要近期登录”的操作（终端、远程管理、模型供应商、MCP 服务）统一改为关键操作。模型 Key 和 MCP 配置从 Hub 的数据库挪到主域加密存放（修改 0016）。

## Alternatives

- **只加强 Hub 的登录（2FA、更短的会话）**：验证者本身被攻破时毫无作用。
- **Hub 留着当大脑，只加签名，不加密数据**：能防控制，防不住数据泄露，不满足“看不到数据”的要求。
- **大脑跑在服务器的机密计算环境里**（SEV-SNP、TDX、Nitro，配合远程证明）：可以保留“Hub 思考”的形态，但要信任 CPU 厂商、承担侧信道风险，成本和复杂度都高。用户有自己的常开机器，没有必要。
- **配对用 PAKE 加短码**：需要在浏览器里实现 CPace 或 SPAKE2，出错的空间大。高熵配对串更简单，安全性也不更差。
- **设恢复码**：用户接受“Passkey 丢了数据就丢了”，换来更少的秘密要保管；推荐的同步 Passkey 已经能覆盖丢一台设备的情况。
- **Cloudflare 托管页面**：用户那边访问慢，而本方案用不到它的数据库和对象存储。

## Consequences

- 服务器被攻破后：控制不了任何机器，读不到任何数据。能做的只有拒绝服务，以及看到元数据（谁在线、什么时候、多少字节）。
- 代价：大脑机器全部离线时 AI 停止工作；关键操作每次都要刷 Face ID；接入新机器要搬运配对串；发版多一步本机签名；中继上的日志排查不了问题。
- 0.3.0 和 0.2.x 的 Node 协议不兼容，所有机器要一起升级，并且要迁移数据（`sous brain import`）。迁移前留在服务器上的明文副本无法保证彻底清除，模型 Key 建议重新生成。
- 设计和任务见 `work/specs/zero-trust`，目标版本 0.3.0-alpha1。
