# Sous 主管能力：主评测协议

本文定义主评测；[可执行 runner](../../tests/e2e/sous-bench/README.md) 和 [历次结果](results.md) 是实现及数据来源。[全链设计](design.md)保留为产品诊断储备，不用其加权分评价主管能力。所有基线、候选默认从 `v0.2.4` 延伸，不测试已废弃的 `v0.3.0`。

## 1. 用同一批题回答两个问题

在每个固定模型配置 `M` 下运行三个实验臂，每题每次重复共用同一初始世界与用户剧本，三臂分别还原状态，块内随机交错执行。

| 臂 | 真正运行的对象 | 要回答的问题 |
|---|---|---|
| `R(M)` | 同一真实模型 + 冻结的最小参考编排器 | 有同等信息机会和操作能力时，这个参考编排能做到什么？ |
| `A(M)` | 基线版本的真实 Sous Hub + 同一真实主管模型 | 旧版主管实际能做到什么？ |
| `B(M)` | 候选版本的真实 Sous Hub + 同一真实主管模型 | 新版主管实际能做到什么？ |

- **主管分** `S = 100 × (在固定预算内严格达成用户目标的任务数 / 有效任务数)`；正式分只比较预先冻结的同套题、同一支持范围，必须同时列分子、分母、覆盖率和门禁。每个独立任务预先指定一次主尝试，额外重复另报稳定性；不得跑完再挑最好那次。必要的澄清、正确拒绝、保持等待、应当不行动，可以是正确结果。自主性、时效和成本同时报告，**不折算进这个分数**。
- **编排差值** `Δ编排 = S(Sous) − S(R)`；正值代表 Sous 比这个参考编排多完成，负值代表少完成。**`R` 不是模型能力上限**，差值不能读成“模型损失了 X% 的通用能力”。用另一个独立设计的参考循环做敏感性复核；若换参考就反号，只报告基线依赖，不宣称普遍限制。
- **版本提升** `Δ版本 = S(B) − S(A)`，用百分点。列 `旧失败/新通过` 和 `旧通过/新失败` 两个方向，不能用净分掩盖关键回归。时延和成本报告绝对差、相对变化及可比样本，不拿新旧平均质量相抵。
- 至少用两套事先选定的真实模型配置复核方向；各模型分别计算三臂结果，不把快慢模型的分数混成一个平均。如果升级只利好一个模型，这就是结论。换模型与换 Sous 版本不在同一个主对照中发生。
- **版本曲线**：每次发布同期重跑上一个版本和固定锚点。报告同时给「较上版」「较锚点」「较参考」三列。只有相同题库、模型快照、profile 和预算的点能连成趋势；模型被停用、题库或关键预算变化时开新批次，有可用的共同版本时重跑建立新锚点，不把前后批次硬拼成曲线。

## 2. 怎样才算同条件

**参考编排器不是裸聊，也不是手写答案的专家代理。** `R` 在 `work/tests/e2e/sous-bench/` 独立实现：通用系统提示、真实模型 tool call → 校验 → 调用工具 → 返回实际结果 → 续轮；只能看到题面、合法观测和工具回执，不能读取 oracle、正确计划、未来事件或完整隐藏状态。不自动补全模型漏写的关键参数，不根据题目类型走捷径。工具作用、参数约束、结果可见性、失败语义和授权要求与 Sous 臂的可比子集相同；参考不依赖 Sous 的主管或任务决策循环。版本原生提示词、上下文选择与工具调度是被测变量，不要求硬改成一模一样。若工具定义与回执序列化不同，记录差异，不能把整包差值直接归因于 prompt 或某一条规则。

两类对照**分开出报告**：

1. **匹配条件档（主报告）**：同一 endpoint、实际模型快照、协议、effort 和可核验请求上限；同一题、语言、用户时钟/行为、环境事件及授权；同等暴露的工具能力与可获得信息（不是把两臂实际输入 prompt 强制相同）。模型调用、输出和墙钟设相同上限，预算在三臂外统一执行；若 API 参数不支持或生效情况无法核实，明确缺口，不称完全匹配。谁主动用掉更多调用和等待是测量结果，不强行给三臂补足调用或补提示。长上下文题必须从同一份原始历史、同一可查询范围开始，不能给参考臂喂已经挑好的事实。
2. **原生部署档（补充）**：各版本按预期部署配置运行，保留其原有工具和机制。结果回答“用户升级实际得到什么”，包含新增能力、默认策略、适配器和成本，不归因成纯编排差值。老版不支持的新能力单独列覆盖及新增题分，不在共通题上静默跳过，也不把“不支持”当同题对照的失败。必测能力因版本不兼容无法对齐时，明确写明无法回答的范围。

### 固定执行与审批，避免测成 worker 排行榜

- 主管必须是真模型；工作 agent 用外部确定性 ACP stub，按可观察的任务指令、机器、权限和执行检查点回结果。它不会替主管修正错误派发、猜出遗漏的约束或保证成功。`R` 使用同一份脚本世界的工作/状态契约；Sous 走真实任务引擎和 Node 通路。实际状态、审批选项及不可逆动作都受同等的测试授权，不拿开了绿灯的参考臂比较保留门禁的 Sous。
- 需审批、验收、用户澄清时用同一个预登记剧本，按状态响应；能显式固定的 reviewer/approver/inspector/compactor 配置都钉住，禁止随主管模型隐式换。全链汇报仍由待测主管产生。测到不同实现的上下文整理策略是允许的，但不能把辅助模型的变化错记为主管变化；现有实现的摘要和静默写记忆可记入相同用量角色，细分需观察实际请求边界。
- A/B 的初始题面、可用工具、授权等都应先预检并记录；版本造成的实际调度、工具回执和可见上下文差异保留为证据，不用适配层修正。固定脚本模型的离线对照只用于复现和验证 runner，不产生主管能力分。

## 3. 首批能力题：从用户目标出题

这些是开发集题族，不是正式盲测题。枪口对准最终世界状态与承诺，并允许不同的正确解。下表覆盖主管最容易改变模型发挥的环节，其他全链题保留，不占主管主分。

| 题族 | 要求 | 独立判据 |
|---|---|---|
| `intent-boundary` | 对类似表述做相反判断：咨询/只计划、可以执行、有关键歧义 | 是否完成正确类型的行动；不应派发时零派发；必须澄清时问到决定性字段且先不动 |
| `plan-dependency` | 多任务含并行、依赖、部分完成的干扰信息 | 检查依赖不变量与有效进度，不要求恰好建 N 个任务；前置失败不偷偷启动受限下游 |
| `route-tradeoff` | 首选机器不可用，备选能力和权限有冲突 | 不派给不能满足硬约束的机器；在允许的候选集合里正确派发，或正确等待 |
| `delegate-constraints` | 向 worker 交接目标、限制和需要验证的证据 | worker 的实际输入与输出状态满足必要约束；遗漏的指令触发可观测失败，不按措辞评分 |
| `repair-after-feedback` | worker 返回部分成功和新增阻塞，需要重排或补问 | 已完成工作不重复；新策略解决真实阻塞，或不冒进地上报；最终验收不信自报成功 |
| `interleaved-updates` | 用户更正原计划的同时另一个话题有独立新消息 | 不能把有效的新约束发给错误任务，不能在旧方案已撤回后继续产生副作用 |
| `long-context-decisions` | 很早给出约束，途中更正，后续把早期原文挤出活跃窗口 | 实际参考到最新证据，任务/汇报与其一致；分别测自动整理前后。判题不要求一定在某个内部步骤压缩 |
| `cross-session-memory` | 新线程按长期约定交付，并穿插更新、删除或相似项目干扰 | 独立 state 检查写入、正确应用与旧值误用；有/无记忆样本共用新线程问题和背景，去掉可找回答案的原文路径，避免答案来自历史搜索；删除不等同于删除聊天史 |
| `bounded-replan` | 多步后遇到可恢复错误，另设重试只会浪费的变体 | 按真实状态重规划、按时完成或明确停手；以成本和延迟旁证，不把调用多等同能力强 |
| `verified-report` | 工具失败或任务等待审批，worker 声称已完成但无凭证 | 最终承诺与可观察事实一致，不能伪报已经执行或交付 |

开发集先用已知正确解、已知错误解和简化基线校验判题，再选真正有挑战的任务；不能根据某个候选的表现挑保留题或改权重。正式按独立任务族隔离一组封存盲题，由未参与调优的人复核**用户需求、等价正确解是否都能过、错误解是否能骗过**；不逐题人工打分。盲题/答案不得进入工作区或模型输入。打开结果后不得删失败题；发现判题 bug 则改版本并补跑所有受影响实验臂。全高分时结论是“这批题区分不出”，保留结果，新增等价但更有挑战的独立任务族并升级题库。

## 4. 从差值追到原因

对每个 `R 过 / Sous 不过` 和 `旧过 / 新不过` 保存可复核 trace：**用户输入 → Sous 组装后的模型可见信息 → 供应商实际请求和工具调用 → 执行结果/被拦原因 → 用户可见终局**。关联 ID、时间戳、调用计数、是否实际触发限次/整理、结构化状态与必要脱敏片段足够，禁止记录凭据和保存无关正文。Hub 的工具回执摘要和事件用于定位；确实需要看到模型请求时，在评测环境用受控 provider proxy，能确定才标已观测。缺数据写 `unattributed`，不凭成败猜原因。

| 观察 | 怎么证明，而不是猜 |
|---|---|
| 模型根本没看到关键信息 | 比对两边可见证据及其来源；用同版本、同模型、同环境的诊断臂，只恢复**本可合法获取**的那段信息再跑。用补回后的差异验证上下文/召回假设，不计入主分 |
| 模型提出了合法动作但没生效 | 用同一已录制的合法模型工具调用在两个版本的独立夹具里重放，检查参数、回执和事件；区分工具注册/ schema、时序、去重与审批分流 |
| 目标还能完成但步数或等待耗尽 | 确认实际触发阈值或批处理等待；参考臂和候选重跑不同预先登记的预算档，画出成功率随预算变化。不要为拿分关闭产品安全防线 |
| 参考过，Sous 因正当授权要求停下 | 正确停下应由 oracle 判通过；若参考偷偷越权则是参考实现/试验无效，不是 Sous 的能力损失 |
| 看到可比信息，执行路径也可用，仍选错 | 先归为模型×编排交互或未归因。需要单变量干预复现，才称某个 prompt、上下文裁剪或调度规则造成退化 |

需要改变产品源码或内部开关才能验证的消融留作后续实验，本 suite 不改 `apps/`，也不把 proxy 下诊断条件混进正式成绩。

## 5. 如何说「提升了多少」

- 正式实验前冻结题库哈希、模型配置签名、运行预算、主对照 (`B−A`)、辅助对照 (`A−R`、`B−R`)、门禁、失效处理和产品关心的最小增益/容忍退化。先做同构建 A/A 和小开发集校准，把可重复性、上游波动、题库难度与统计分辨能力写清楚；小 pilot 能发现机制问题，不能读出百分之几的提升。
- 对每个预登记的独立任务主配对求 `d = B的成功标记 − A的成功标记`。若有变体和重复，把同题族保持在同一聚类块；报告任务族数量、配对尝试数、净变化、两向翻转和按任务族配对的 95% 区间。样本过小、极端饱和或重采样退化时，不把零宽区间发布为精确结论；改用预定的保守区间或标 `insufficient` 并补独立题。区间只描述声明的评测分布，不代表全部真实用户需求。
- 明确区分 `提升`（区间下界超过预登记的实用增益）、`退化`（上界低于负容忍值）、`证据支持变化在容忍范围内`（整个区间落在预设容忍区间）和 `不确定`。发布门禁可另外要求最小质量、零硬违规，以及达成 P95/成本目标；不以“没有显著差异”宣布两个版本一样好。
- 应用可观察的失败、超时和合规性的误判留在分母；评测器坏了或有无法核实的缺题不得报正式分，完整记录。供应商失败单独归因；只在双方供应商可用时的结果是辅助敏感性分析，不替换主报告。强制披露质量、干预数、模型调用、每成功任务用量和墙钟/尾延迟，区分成功样本延迟与全样本超时率。

**报告格式示例（纯示意，不是数据）：**

| 模型 | 参考编排 | 基线 Sous | 候选 Sous | 候选 vs 参考 | 候选 vs 基线 |
|---|---:|---:|---:|---:|---:|
| 模型 M | 76/100 | 64/100 | 72/100 | −4 pp | +8 pp |

若其中 13 题由失败转通过、5 题由通过转失败，净值就是 +8 pp；没有区间前不能判定提升。读报告必须同时看到覆盖、区间、5 个反向变化和单位成功任务成本。

## 6. 已实现的评测范围

- `supervisor-v2`：17 题、每题每臂一次，输出分项、双向翻转和诊断证据；同一可比签名支持历史重算，但升级判断优先同期配对。较前述长期实验协议，当前 runner 还没有提供聚类重复、独立盲测集、原生部署档和阶段级账单。可选更多模型端点逐次单独跑三臂，不自动合并其结果。
- `v0.2.4` 与参考是首次主对照；从 `v0.2.4` 开发的候选 commit 可传入同批对照。已废弃 `v0.3.0` 不纳入实验。没有满足相同条件的候选结果时不写版本增幅；没有真模型有效的结果时不以 mock 顶替。
- 测试代码和合成数据都在 `work/tests/e2e/sous-bench/`，逐题证据在 `work/logs/sous-bench/`，摘要自动追加到 [结果表](results.md)。仅消费临时二进制和接口，不修改 app。首轮判题审计见 [基线记录](baseline-v0-2-4.md)。
