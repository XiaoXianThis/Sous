# 0020 长对话的上下文：分段、结构化摘要、查回原文

- Status: Accepted
- Date: 2026-11-05

## Context

主线是一条不会结束的对话。原来每轮只取最近 40 条消息，再把时间、机器、任务和召回的记忆写进系统提示：

- 第 41 条以前的内容直接看不见，没写进记忆的决定和承诺就丢了；
- 按条数截，不按 token 截，几条大消息就能撑爆窗口；
- 系统提示每轮都变，后面的历史消息几乎不命中提示缓存（实测最近 20 次调用的命中率只有 14%）。

## Decision

- **请求结构固定**：系统提示和工具定义不含任何每轮会变的内容。每轮会变的时间、机器、任务、召回的记忆，作为“本轮环境”接在最新那条用户消息后面，只发这一轮，不存。
- **分段**：一条对话的上下文分成若干段（`thread.compacted` 事件，`thread_segments` 表）。每段开头是一条“段首块”：画像记忆的快照加摘要。之后的消息原样发送。同一段里请求只在末尾追加，所以能一直命中缓存；Anthropic 用 `cache_control` 在系统提示、段首块和最新消息前打断点。
- **按 token 触发整理**：估算超过窗口的 60% 时，回合结束后整理；超过 85% 时先整理再回复；模型报上下文超长时整理后重试一次。整理失败就从最老的消息开始略去，不报错给用户。窗口大小是模型角色上的 `context_window`。
- **整理 = 先写记忆，再写摘要**：先跑一轮静默回合，只开放记忆工具，把要折叠的内容里值得长期记住的写进记忆；再由 `compactor` 角色（默认跟主管同一个模型）把旧摘要和要折叠的消息合成新摘要。
- **摘要按固定栏目写，每条带来源编号 `[#seq]`**。“已做的决定”“待办和承诺”里的条目只能移到“已完成或作废”，不能消失；程序会校验，有遗漏就让模型重写一次，还漏就由程序把它补回去。
- **原文可查**：`thread_search`、`thread_read` 两个工具按关键词和编号查回原文。

## Alternatives

- 固定条数的滑动窗口（原做法）：简单，但会健忘，开头每轮都在变，缓存命中不了。
- 全部历史都发：成本随对话长度线性增长，终究会超出窗口；上下文太长时，模型对中间那段内容的注意力也会下降。
- 按天重置会话（OpenClaw 的做法）：主线的价值就在连续，不重置。
- 向量检索召回旧消息：单用户的消息量用子串匹配就够；摘要里的编号可以直接定位原文，以后有需要再加。

## Consequences

- 实测（DeepSeek）同一段内每次调用的缓存命中在 87% 到 99% 之间；换段那一轮系统提示和工具定义仍然命中。
- 每次整理多两到几次模型调用（写记忆和写摘要），用量按 `compactor` 角色记录。
- 摘要是有损的：细节靠 `[#seq]` 和查回原文的工具补；摘要可以在页面上查看和修改。
- 启用前已经很长的对话，第一段从最近能放下的消息开始，更早的没有摘要，但可以搜到原文。
