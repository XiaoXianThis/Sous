# Sous 主管 Benchmark：需求与验收口径

## 要回答的问题

1. **现在多可靠？** 给 Sous `v0.2.4` 的主管能力一个可复算的真模型成绩，列出哪类任务过/不过、人工门禁、耗时与用量。不要把夹具或模型自报成功当作实际成功。
2. **编排帮助还是限制模型？** 用同一端点、同一模型、同一题及共同工具，对照最小参考编排器。差值只表示两种实现和该模型的交互，不把参考当模型能力上限，也不凭一次输赢归因到某段代码。
3. **升级提升多少？** `v0.2.4` 是固定基线，`v0.3.0` 不测。后续用候选 commit 与基线同期配对，报告通过率百分点差、区间、修好的题、弄坏的题、硬门禁及资源代价。同题切换模型时重跑每个实验臂，分别报告，不按不同模型的历史裸分归因。
4. **记忆可靠吗？** 不只测“记住”：测长期写入/无关信息不写入、新话题读回、无记忆不编造、更正、忘记、相关性，以及同一线程上下文整理后保留更正。

## 交付与判定

- 基准流包含意图理解、规划与边界、委派与机器选择、依赖、根据实际失败改派、人工验收与事实汇报、六道长期记忆和一道上下文整理题。用户脚本和 worker 固定，判题读取真实 Hub 状态、确定性 ACP worker 退出与实际产物，以及约束、因果顺序和副作用。没有大模型裁判。
- 主分是全题严格完成率（0–100，无主观加权）；一道题所有必要断言通过才计一分。硬失败单列，不能被得分抵消。模型/产品可观察失败不踢出分母；评测器失败、缺臂、缺题或模型身份漂移时不补零、不发布有缺口的正式对照。所有有记录的失败均保留。
- 成功样本 P50/P95、模型请求延迟、调用总量及 token 覆盖独立报告。小样本不报不可靠的 P95；订阅未暴露的货币成本不猜测。该流不测生产吞吐、真实 worker 编程质量、部署交付或产品原生首 token 时间。
- Bun runner、自动断言和测试只放在 `work/`；历史构建从 Git 对象在临时目录进行，不写 `apps/`，不接生产状态。一个命令启动隔离环境、运行、判分、自动写入[成绩表](results.md)；单次证据详见 runner 文档所列归档路径。预备模型凭据后不需要人工逐题打分。
- 验收分开看：离线黄金路径与负对照证明判题器能分辨成功和伪成功，`v0.2.4` 真模型成绩才记为主管能力分。没有真模型重复或盲测时，结果仅作为原题库/模型的固定基线，不用来宣称精确的线上差异、普适排名或万无一失。

具体命令与当前覆盖：[runner](../../tests/e2e/sous-bench/README.md)。对照设计与未来可扩展实验见 [主管评测协议](supervisor-evaluation.md) 和 [全产品扩展设计](design.md)。
