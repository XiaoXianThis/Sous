# sous 端到端体验测试报告

- 测试日期：2026-11-05
- 代码版本：`3074616`（main）
- 测试环境：macOS，Hub `127.0.0.1:8787`（dev），web dev `127.0.0.1:5173`，生产构建 `127.0.0.1:8787`
- 测试方式：浏览器（桌面 1024×720、手机 390×844）、`sous` CLI、真实 Hub/daemon/agent、脚本构造的多项目多机器场景

## 0. 结论

**总评：6.9 / 10。方向正确，单人多项目和跨设备体验已经成立；主要短板是“自动化不可完全信任”。**

- 一个人同时盯多个项目：**7.0/10**。工作台的项目卡片、实时 agent 卡、项目对话和审批流已经能把多个项目收在一个屏幕里；但收件箱噪音、缺少全局搜索/全局运行视图，项目一多就会退化。
- 多设备互通：**9.0/10**。手机发消息 3 秒内出现在桌面浏览器和 `sous chat`，历史、上下文和回复都连续；这是本次测试里最扎实的部分。
- 开发到部署一条龙：**6.0/10**。代码任务 → 自动验收 → push/PR → 合并 → 手工/自动部署在机制上跑通了；但部署任务会在 agent 额度耗尽、实际上什么都没做时被标记为“完成”，部署阶段也会显示绿色对勾，属于会误导人的失败。
- 可靠性与自主运行：**4.5/10**。对 agent 空回合、额度耗尽、用户拒绝权限、机器并发占满这些真实情况，系统的处理和 UI 都不够可靠；自动化越“自主”，误报成功的代价越大。
- 审批与安全：**7.5/10**。底线规则、本地复检、AI 审批、服务器角色降级、近期登录验证 Passkey 都很扎实；差在审批卡的信息呈现和中文一致性。
- 交互与视觉：**8.0/10**。桌面三栏和手机原生感都做得好，状态色/图标/间距统一；细节上有多处“说一套、做一套”的小问题。
- 可观测性与成本：**6.0/10**。用量页按角色/模型统计清楚，长对话有上下文/缓存指标；但运行日志没有工具输出和错误，agent 自己的用量和计划限制不可见。
- 性能与可访问性：**7.0/10**。生产构建单包 1.34 MB（gzip 399 KB），无代码分割；Lighthouse Accessibility 90，深色模式的次要文字对比度不达标。
- 工程与发布卫生：**6.5/10**。Hub 当前托管的 `build/web` 一度是 09:19 的旧构建（缺 PNG 图标、缺新 viewport/manifest），重新构建后才与源码一致；这类“测的不是最新包”的风险需要流程兜底。

一句话：**现在是一个好用的个人 AI 工作台，但还不是一个可以放心无人值守跑生产的系统。** 先修 P0 的“假成功/重试循环/交付排队/归属显示”，整体可以到 8 分级。

## 3. 体验亮点

1. **多设备连续性是真实可用的。** 手机发“现在有几个项目、几台机器在线？”，桌面 WebSocket 在 3 秒内出现同一条消息和回复；`sous chat` 里也能看到同一条记录。同一个线程、同一份上下文，不需要“同步一下”。
2. **工作台的信息密度和视觉层级很好。** 项目卡 + 运行中的 agent 卡 + 任务行 + 审批卡放在一屏，桌面三栏和手机底部玻璃标签栏都很像成熟产品；浅色/深色都成立。
3. **审批分级是有效的。** AI 审批能准确说出“这是本地 Go 改动，不需要联网搜索”并升级给用户；服务器上的 `./deploy.sh` 也会因为看不到脚本内容而升级。这不是装饰性的“AI 审批”。
4. **reviewer 的质量超出预期。** 它没有只看 agent 的自述，而是指出“只新建了 hello.txt，没实现折线图”“没有执行 git status/git log”，并给出可执行的返工要求；通过时也能准确说明改了哪一行。
5. **完整闭环机械上跑通了。** Claude 改代码 → reviewer 通过 → push → PR → 本地合并 → 手工部署 → 8899 页面出现新 footer；运维任务在 Oracle 上真实执行 `./check.sh` 并汇报磁盘/服务状态。
6. **项目管理做得细。** 归档/激活、项目位置、部署目标、健康检查、自动部署开关、合并后部署、运行中追加消息、暂停/继续都在。
7. **远程 agent 管理是差异化能力。** 在机器页里能看 agent 版本/登录状态、改模型与思考强度、填 API Key、编辑配置文件，不需要 SSH。
8. **用量页诚实。** 明确写出“只统计 sous 自己的模型调用，编程 agent 的用量在各自账户里”，没有把不可见的成本算进来。
9. **安全基础扎实。** CSP、X-Frame-Options、COSR、Permissions-Policy、Passkey 再验证、服务器角色不允许 open 模式、底线规则本地复检。

## 4. 问题清单

### P0：会破坏信任，必须优先修

#### 4.1 运维/部署任务“假成功”：agent 额度耗尽、什么都没做，任务却显示完成

**现象**

- `清理 /var/log 下 30 天前的日志`（ops）：任务状态 `done`，阶段条“执行/健康检查”全绿，Run 摘要只有 `Upgrade your plan to continue`。实际没有列出文件、没有删除、没有任何审批。
- `部署「api-gateway」：/healthz 增加数据库连通性检查`（ops，自动部署）：任务 `done`，Run 摘要 `Upgrade your plan to continue`；服务器上 `git log` 仍停在 `b0544e0`，`curl :8898/healthz` 无响应。
- 两个任务的 Run 状态都是 `succeeded`，因为 agent 以 `end_turn` 结束了回合；引擎把“正常结束”当成“工作完成”。

**证据**

- 任务 `01M6NGHZX612FRKD0XH7BZS77J`，Run 摘要 `Upgrade your plan to continue`。
- 任务 `01M6NHQPEHW5EBTHV436JY5P2H`，Run `01M6NHQPETXQWVHQS25D0A4MZ6`，摘要同上；服务器 `srv/api-gateway` 的 HEAD 仍是 `b0544e0`，8898 无服务。
- 代码任务 `/healthz 增加数据库连通性检查` 的阶段条“部署”显示绿色对勾；依据只是“项目里存在一个在任务之后创建的 ops 任务”，没有检查这个 ops 任务是否成功、健康检查是否通过。

**影响**

- 用户会以为部署/清理已完成，实际线上没有变化；这比直接报错更危险。
- 与“sous 永远不合并 PR、部署由用户把关”的信任模型冲突：用户把部署交给系统，系统却回报了一个没有发生的成功。
- 同样的问题会出现在所有“以自然语言摘要结尾、实际没有执行动作”的 agent 回合上，不只是额度耗尽。

**建议**

1. 在 Node/ACP 层增加“回合结果分类”：识别 `usage limit`、`quota`、`rate limit`、`Upgrade your plan`、`Service temporarily unavailable`、`monthly usage limit` 等已知文本，映射成结构化错误（如 `agent_quota`），Run 标记 `failed` 而不是 `succeeded`。
2. ops 任务不能只凭 `end_turn` 完成：要求部署命令/健康检查至少有一次带退出码 0 的工具调用，或让 Node 在 Run 结束后做一次独立的健康检查；检查不通过就 `blocked`，并说明“未验证”。
3. 代码任务增加“空产出”判定：如果 diff 为空且任务不是只读/调研类，标记失败/受阻，不要进入 reviewer 后再次重试。
4. 任务完成状态由“Run 成功 + 验收通过 +（代码任务）交付成功 +（部署）健康检查通过”共同决定，任何一环失败都不要把阶段条画绿。

#### 4.2 用户拒绝审批后，任务会重新排队并再次请求同一个权限

**现象**

- 在 web-analytics 的假 agent 任务上，第一次 `Write hello.txt` 审批点“Reject”。Run 以“没有获得写入权限，已停止”结束，reviewer 以“没有实际改动”打回，任务自动 `review → queued → running`，又创建了一个**新的审批**（新 id，同样标题/命令）。
- 手机上再拒绝一次，同样再次重试；直到手动取消任务才停止。
- 这也意味着用户永远无法通过“拒绝”表达“不要做这个”；系统把拒绝当成一次失败尝试，继续消耗 token 和时间。

**影响**

- 审批的语义被破坏：用户拒绝不是终点，而是一个新的重试信号。
- 在无人值守场景会形成“请求 → 拒绝 → 重试 → 再请求”的循环，产生重复通知和费用。
- 与“最少注意力”原则相反。

**建议**

- 审批结果为 `reject` 时，直接结束该 Run，并把任务置为 `blocked`（原因：你拒绝了这一步），不要自动 requeue；提供明确的“重试/换 agent/换机器”按钮让用户再决定。
- 记录 `rejection_count` 和最近一次拒绝的 approval 指纹；同一个任务对同一个工具/命令的审批不能重复弹出，除非用户主动重试。
- 如果 agent 因权限被拒而结束，reviewer 不应把它当作“可重试的失败”，而应保留用户意图。

#### 4.3 交付（push/PR）会被机器并发名额卡住，已完成的任务迟迟不能进入 PR

**现象**

- Claude 任务通过验收后，事件为 `from: review, to: queued, reason: 等待机器：MacBook-Air 正忙, next: deliver`；因为同一台机器上还有两个 Run（一个审批中、一个假 agent）占满 2 个工位，交付 Run 排队；手动取消其中一个 Run 后，交付立即成功。
- 交付本质上不需要 agent，也不产生代码，但仍然按普通 Run 计入 `Busy`/并发上限。

**影响**

- 用户看到“任务已完成”但 PR 还没开，容易误以为交付失败或系统卡住。
- 一个长任务占着工位时，其他项目的交付会排队，直接损害“一个人多项目”的吞吐。
- 与“验收通过后自动交付”的预期不符。

**建议**

- `deliver`/`rebase` 不计入工作区并发，或使用独立的小并发池；至少给交付最高优先级。
- 在 UI 上把“等待交付”与“等待机器执行”分开显示；交付排队时提供“立即交付”按钮。
- 如果交付只需要 git，可以在验收通过的同一个 Node 上直接执行，不必新建一个“sous” Run。

#### 4.4 任务行显示的 agent 与实际执行者不一致

**现象**

- `页脚加上版本号和部署环境` 实际由 Claude 完成（Run `01M6NH203SZ4WW6AQ8E9RW4X68`，agent=`claude`），但工作台任务行、项目卡任务行、归档卡都显示 **OpenCode**。
- `/healthz 增加数据库连通性检查` 实际由 Cursor 完成，任务行显示 Cursor（碰巧正确，因为后端岗位默认就是 Cursor）。
- 原因：任务行在拿不到当前 Run 时回退到岗位默认 agent；已完成任务往往没有“当前 Run”，于是显示的是岗位配置，而不是最后一次实际执行者。

**影响**

- 无法回答“这个改动是谁做的”，在换 agent/换机器排障时尤其致命。
- 审批、成本归因、复盘都会跟着错。

**建议**

- 在任务投影里记录 `last_run_agent`/`last_run_node`（最后一次 work/rebase Run），任务行优先显示它；岗位只作为头像/默认值。
- 任务详情里同时显示“岗位”和“实际执行 agent/机器”，例如“前端 · 由 Claude 在 MacBook-Air 完成”。
- 加一个单元测试：agent_pref 与岗位不同、最后一次 Run 缺失/交付 Run 在后，任务行仍显示正确的执行 agent。

#### 4.5 “部署”阶段按“存在 ops 任务”判定成功，而不是按部署结果

**现象**

- api-gateway 的代码任务阶段条显示“计划/编码/验收/PR/部署”全绿；但它的自动部署 ops 任务实际失败（见 4.1），服务没起来。
- `deployedAfter` 只看有没有在任务之后创建、未取消的 ops 任务，不看 ops 任务的状态、健康检查或部署输出。

**影响**

- 阶段条是用户判断“到哪一步了”的主要视觉语言，这里给出了错误的结论。
- 用户会把“部署”当成已验证事实，错过回滚窗口。

**建议**

- 任务投影增加 `deploy_state`（none/queued/running/done/failed/skipped）；阶段条只在该 ops 任务 `done` 且健康检查通过时画绿；失败时显示红色/受阻并提供“查看部署日志”。
- 自动部署 poll 失败/健康检查失败要通知用户，不能静默停在 done。

## 6. 后续优化建议

### P0（先修，直接影响信任）

1. **agent 回合结果分类 + ops 验收**：识别额度/限流/不可用文本，Run 标失败；ops 必须有部署命令退出码或独立健康检查，否则 `blocked`。
2. **拒绝即停止**：审批拒绝结束 Run、任务 `blocked`；同任务同指纹不重复请求；给用户“重试/换 agent/换机器”显式按钮。
3. **交付独立于工作并发**：`deliver`/`rebase` 不占工作工位或高优先级；UI 区分“排队交付”和“等待机器”。
4. **归属与阶段真实**：任务行显示最后实际执行 agent/机器；`deploy_state` 驱动阶段条；空 diff 不算成功。
5. **空产出防护**：代码任务 diff 为空且非只读 → 失败/受阻；不要进入 reviewer 重试。

### 7.3 建议的真实环境验收清单

1. 真实 GitHub 私有仓库：创建 → 任务 → PR → 在 GitHub 合并 → 自动部署 → 健康检查。
2. 真实手机（iOS PWA）：安装、推送、审批、终端 Passkey 再验证、断网/恢复。

4. 强杀 daemon/Hub：任务恢复或正确失败；通知不丢。
5. 巡检：制造 loop agent，10 分钟内暂停并通知。
