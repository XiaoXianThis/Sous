# 0027 对话按话题整理：一份上下文，按话题分轮和显示

- Status: Accepted
- Date: 2026-11-09

## Context

主线是一条按时间排的消息流。用户习惯同时开好几件事，每件事的任务执行时间不同，汇报、叫醒、主管的评论按完成时间交错出现，议题一多就要自己拼回来。主管回合进行中发来的消息只能等这一轮结束，再和其他未回复的消息合成一次回复：补充来晚了（任务可能已经按旧要求派出），不相关的事也被混进同一次回复。主管和子 agent 之间说了什么也看不到。

## Decision

1. **话题是线程里的标签，不是新线程。** 每条消息属于一个话题（`messages.topic_id`），任务也属于一个话题（`tasks.topic_id`）。主管仍然只有一份上下文（决策 0020 的分段和摘要不变），历史里用户消息前加 `【话题#N】`（N 是话题第一条消息的 seq，不会变），不同话题之间可以互相参考。没有采用“每个话题一个独立主管”：那样会丢掉跨议题的判断，花费也会翻倍，项目对话已经承担了“隔离上下文”的角色。
2. **开话题不需要单独的事件。** 没有话题的用户消息、trigger、汇报、通知、巡检提示自己开一个话题，话题 id 就是消息 id，投影是确定的。之后的变化走 `topic.updated`（标题、当前结论、开关）和 `message.moved`（并入和撤销）。用户消息、trigger 和这几类通知会把关闭的话题重新打开，主管自己的回复不会。
3. **一轮只回答一个话题**，最早有未回复消息的话题先来。请求里不放其他话题还在等的消息，它们在各自的回合里处理，所以每个回复都跟在自己的消息后面。
4. **插话由主管判断。** 回合进行中，每次调用模型之前读新消息：同一话题里的当作补充插进去；在全局输入框发的、自成新话题且只有一条的，当作“可能的补充”插进去，主管用 `topic_attach` 并入，否则它在这一轮之后单独处理；回合开始前几秒内连发的也这样提供。插入的文字追加在最后一个工具结果后面，各家接口都接受，不入库。用户可以撤销并入，消息回到自己的话题，主管单独回答。
5. **有副作用的操作先等新消息。** 模型决定调用工具的同时用户发来了要插入的消息，而调用里有不在只读名单里的工具（含 MCP 工具）时，这一批都不执行，把消息给模型看完再决定。
6. **主管维护话题的状态**：`topic_update` 写一两句“当前结论”，`topic_close` 关闭并总结。界面按“要你处理 > 进行中 > 已结束”排话题卡片。
7. **主管 ↔ 子 agent 的沟通可以查看**：派发和返工的提示词、追加指令、进度、提问、结果、验收、汇报，从任务的事件里按顺序列出（`GET /tasks/{id}/talk`），界面上默认收起。
8. **推送按话题合并**：同一话题的通知用同一个 tag 互相替换，链接直接打开话题。

## Consequences

- 话题之间只在界面上隔开，主管仍然看得到全部历史；话题标签写在消息里，同一段内请求的前缀仍然只往后追加（R3 / 0020）。
- 插话和并入依赖模型的判断，会判断错，所以并入必须可撤销、在界面上看得见。
- 主管回合还是一个接一个地跑；一轮如果很长（比如主管自己查很久的资料），后面的话题要等。长活应该交给任务或顾问。
- 旧消息没有话题，在界面上归为“更早的对话”。
