# 设计

## 原则

上下文只是工作区，不是全部历史。事件日志保存全部历史，记忆库保存长期事实，任务和项目表保存状态。每轮发给模型的只有四样：固定部分、一份结构化摘要、摘要之后的原文、本轮环境。更早的细节靠工具查原文。

一条线程的上下文分成若干**段**：每次整理都会开始新的一段。段内的请求前缀只追加、不修改，所以缓存一直命中；换段时前缀整体重建一次。

## 1. 请求结构（R3）

```
system   [固定提示词]                          按线程种类和项目固定；不含时间
tools    [工具定义]                            已按名字排序（tool.Registry.Specs），保持不变
messages [段首块：画像记忆快照 + 摘要]          一条 user 消息，只在换段时变化
         [摘要之后的原文消息 ...]               只往后追加
         [最新用户消息 + 本轮环境]              只有这一条每轮都变
```

- **系统提示去掉所有会变的内容**：当前时间、机器、项目、任务、召回的记忆，全部移到本轮环境。项目对话的“作用域”一节按项目固定，可以留在系统提示里。
- **本轮环境**拼在最新那条用户消息后面，用 `【本轮环境】…` 隔开，只在本轮发送，不存进消息表。内容包括：
  - 当前时间（精确到分钟）；
  - 机器、项目和任务；
  - 按最近用户消息召回的相关记忆；
  - 本段内新增或修改过的画像记忆。
  
  下一轮它会被丢掉，从上一轮的用户消息开始，前缀和上一轮完全一样，所以只有最后一小段不命中。
- **画像记忆快照**在开始新的一段时读一次，写进段首块。段内新存的画像记忆通过本轮环境补上，下次整理时并进快照。这和 Hermes 冻结 `MEMORY.md` 的做法相同。
- **用户在工作台上看的东西**（`MessageContext` 前缀）照旧写在那条消息里：它本身就是消息的一部分，以后每轮都一样，不影响缓存。
- **Anthropic**：`provider.Request` 加一个可选字段 `CacheAt []int`（消息下标），Anthropic 实现据此在对应位置加 `cache_control: {type: ephemeral}`。断点放在三处：
  1. 系统提示和工具定义末尾；
  2. 段首块末尾；
  3. 倒数第二条消息（滚动断点）。
  
  OpenAI Chat、Responses 和 DeepSeek 不需要标记，忽略这个字段。

## 2. 段和摘要（R1、R2）

新事件 `thread.compacted`（执行者是 supervisor，或者用户手动编辑时是 user）：

```json
{"segment": 3, "covers_up_to": 18842, "summary": "…", "profile": ["[m1] (profile) …"],
 "reason": "soft|hard|overflow|manual|edit", "input_tokens": 61234, "model": "…"}
```

- 投影到新表 `thread_segments(thread_id, segment, covers_up_to, summary, profile, created_at, event_seq)`（迁移 10）。
- 每轮取线程最新的一段，加上 `event_seq > covers_up_to` 的所有消息。`HistoryMessages = 40` 这个上限去掉，改成按 token 预算控制（见 §3）。还没整理过的线程，第 0 段为空摘要，从头开始。

### 摘要格式

按固定栏目写，每条后面带上来源消息的编号 `[#seq]`：

```
## 已做的决定
- 主线部署到 agent.wxian.cc，用 Caddy 反代 [#1203][#1240]
## 待办和承诺
- 周五提醒用户续费域名 [#1388]
## 用户的偏好和纠正
- 回复用中文、要简洁；不要自动合并 PR [#310][#977]
## 进行中的话题
- 正在讨论多机同步的冲突提醒怎么展示 [#18790]
## 已完成或作废
- （本次整理时从“待办和承诺”移出的条目，带完成时的 [#seq]）
## 其他背景
- …
```

- 输入是旧摘要加上这次要折叠的原文消息，输出是新摘要。规则（写在整理用的提示词里）：
  - 旧摘要里仍然成立的条目原样保留；
  - 只有已完成、已作废或被推翻的条目才能删掉，并且要移到“已完成或作废”栏，写明依据；
  - “已完成或作废”只保留本次整理移出的条目，下次整理时清空；
  - 摘要上限约 3000 token。超出时先压缩“其他背景”和“进行中的话题”，前三栏不压缩。
- **程序校验**：解析新旧摘要的栏目。旧摘要“待办和承诺”和“已做的决定”里的每一条，必须出现在新摘要的同一栏或“已完成或作废”栏（按 `[#seq]` 和文本相似度匹配）。有遗漏时，把遗漏的条目告诉模型重试一次；还有遗漏，就由程序把这些条目原样追加回对应栏目，宁可多留也不丢。

### 用哪个模型

新增角色 `compactor`（页面上叫“整理”），没配置时用 supervisor 的模型（和其他角色一样，遵循 0016）。用量按 role=`compactor` 记录。

## 3. 何时整理（R1、R5）

- **上下文窗口**：模型配置加一个 `context_window` 字段（页面可填），默认 128k。
- **估算本轮输入**：取这条线程上一次调用的 `InputTokens`（`usage.recorded`），加上之后新增内容的估算（中文每字按 1 token，其他文字每 4 字符按 1 token，宁可高估）。线程还没有调用记录时，全部按估算算。
- **三种触发**：
  - **软阈值 60%**：本轮回复完成后，在线程自己的串行队列里整理，用户不用等。整理期间新到的消息照常排队。
  - **硬阈值 85%**：本轮开始前先同步整理，然后再调用模型。
  - **溢出**：模型返回上下文超长错误时，整理一次，然后重试，只重试一次。
- **折叠范围**：保留最近的原文，至少 10 条用户消息，并且不少于预算的 25%。比这更早的、在 `covers_up_to` 之后的消息全部折叠。
- **降级**：整理失败（模型报错、校验重试后仍然失败）时，记一条警告，本轮按 token 预算从最老的原文开始丢弃，保证不超过 85%。下一轮软阈值会再试。连续失败 3 次后给巡检员一条发现（finding）。
- **大消息**：单条消息超过 4000 字时，组装历史时只保留开头 1500 字和结尾 1500 字，中间换成 `【中间省略 N 字，用 thread_read #seq 看全文】`。消息表里的原文不动。

## 4. 整理前写记忆（R2）

折叠前先跑一轮静默回合：

- 模型是 supervisor；只开放 `memory_save`、`memory_search`、`memory_forget` 三个工具；
- 输入是要折叠的原文和现有画像记忆；
- 提示词：“下面这段对话即将折叠成摘要。把值得长期记住的事实、偏好、决定写进记忆；已有的就更新，不要重复；不用回复用户。”

这一轮不产生消息，只产生 `memory.*` 事件，用量按 role=`compactor` 记录。然后再生成摘要；新一段的画像快照包含刚写进去的记忆。

## 5. 查回原文（R2）

两个新工具，只读，所有线程都可用：

- `thread_search {query, limit?, scope?}`：在当前线程的消息里搜索，返回 `[#seq] 时间 角色：片段`。`scope: "all"` 只在主线可用，范围是所有线程。匹配方式和 `SearchMemories` 一样（中文按两字词、其他按整词子串匹配），按命中长度排序，最多返回 10 条。
- `thread_read {seq, before?, after?}`：读某条消息的全文，以及它前后若干条（默认前后各 3 条，最多 20 条）。

系统提示里说明：“更早的对话已经整理成摘要。需要原话、数字或细节时，用 `thread_search` / `thread_read` 查，不要凭印象回答。”

先不建全文索引：单用户的消息量在十万条以内，`instr` 扫描足够快。等实测太慢了，再换成 FTS5 trigram。

## 6. 页面和接口（R4）

- `GET /api/threads/{id}/context`：返回当前段号、摘要、`covers_up_to`、估算的占用和窗口大小、最近 20 轮的缓存命中率（由 `usage.recorded` 汇总）、上次整理的时间和原因。
- `POST /api/threads/{id}/compact`：立即整理，原因记为 `manual`。
- `PUT /api/threads/{id}/summary {summary}`：用户编辑摘要，产生一个 `thread.compacted` 事件，原因记为 `edit`，`covers_up_to` 不变，并开始新的一段。
- 主线页面：
  - 标题栏显示一个小占用环（悬停看百分比和命中率），点开是“上下文”面板：摘要（可编辑）、占用、命中率，以及“现在整理”按钮。
  - 消息列表里，`covers_up_to` 的位置显示一条分隔线“以上内容已整理进摘要”，点它打开面板。往上依然能翻全部历史。

## 7. 并发

整理总在线程的串行队列里执行（`Supervisor.queues`），和正常回合不会并发。软阈值整理也作为队列里的一个任务排在回复之后。静默写记忆和摘要两次调用都受 Hub 的 context 控制，Hub 关闭时放弃，下次重启后由软阈值重新触发。

## 实现时的调整

- token 估算只用字数估算（中日韩文字 1 字 1 token，其他 4 字符 1 token），回合前的硬阈值只看估算；回合后的软阈值取估算和上一次调用实际输入中较大的一个。实测估算比 DeepSeek 实际值高约 20%，宁可早整理。
- 本轮环境作为最新用户消息里单独的一个文本片段（`Part`）发送，系统提示标题改成“当前对话”，提示词里说明了段首块、`[#seq]`、查原文工具和本轮环境。
- 线程第一次进入新机制时自动建第 1 段（原因 `start`）：旧对话太长时，第 1 段从最近能放下的消息开始，更早的部分没有摘要（摘要里写明了可以搜），不在启动时一次性补整理。
- 折叠规则按原因区分：手动整理只要求保留 10 条用户消息，不要求 25% 的 token；模型报超长后只保留 4 条用户消息。要折叠的内容超过窗口 35% 时分块，逐块写记忆、更新摘要。
- 连续 3 次整理失败不发巡检发现（巡检发现是按 Run 的），而是在这条对话里发一条提示。
- 画像快照最多 30 条记忆；召回的相关记忆不再重复快照里已有的。
- `PUT /models/roles` 不带 `context_window` 时，模型没变就保留原来的窗口（聊天标题旁的模型切换不会把它清掉）；窗口只在主管那一行设置，`compactor` 跟随主管。
- 上下文面板用 `Sheet`（桌面居中弹窗、手机底部抽屉），占用环放在聊天标题栏里模型名的左边；手机上模型名可以缩短，对话名不被挤掉。
- Anthropic 的 `InputTokens` 现在也算上写缓存的 token（`cache_creation_input_tokens`），否则占用会被低估。

## 8. 不做的事

- 不用向量检索或 embedding，现有的子串匹配加 `[#seq]` 引用已经够用。以后要做，单独写 spec。
- 不按天自动重置会话（OpenClaw 有这个功能）：主线就是要一直连续。
- 不把项目对话的摘要汇总进主线。
- 不把回合中间的工具调用和结果写进历史（维持现状）。
