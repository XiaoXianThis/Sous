# 0029 会议：在独立上下文里讨论，散会后把纪要交回对话

- Status: Accepted
- Date: 2026-11-11

## Context

需求不确定时，用户要和 sous 反复讨论。在主线或项目对话里讨论有几个问题：

- 讨论很长，挤占上下文窗口，提前触发整理（0020）；
- 讨论中途被否掉的想法会进入摘要和长期记忆，之后误导主管；
- 话题（0027）只在界面上把讨论隔开，主管的上下文仍然是同一份。

## Decision

1. **会议是一条独立的对话**（线程 `kind: meeting`），有自己的上下文、分段和摘要，记下它来自哪个对话和话题。开会只带一份简报（父话题的当前结论、相关摘要、开场问题），不带整条对话。
2. **会议只讨论，不做事。** 主持人默认是 sous，用会议专用的提示，只能用只读工具，不能建任务、不能做 git 操作。可以请项目顾问或任务的 agent 参会。
3. **主管可以提议开会，但不能自己开会。** 由用户确认后才开始。
4. **散会时生成纪要**，栏目固定：议题、结论和决定、被否掉的方案和理由、未决问题、行动项。每条带 `[#seq]` 指向会议原文；结论和行动项经过程序校验，不会遗漏。纪要默认要用户确认后才发出，设置里可以改成直接发出。
5. **纪要发到父话题，并叫醒主管**，由主管处理行动项。主管可以按 `[#seq]` 读回会议原文，但只能读当前对话关联过的会议。
6. **会议进行中不写长期记忆**，纪要进入父对话以后才跟着父对话的整理流程处理记忆。
7. 已经结束的会议可以续会，生成修订版纪要，替换父话题里的那份。

## Alternatives

- **每个话题一个独立主管**：0027 已经否决（丢掉跨议题的判断，花费翻倍）。会议是用户主动要求的隔离，次数少、有明确的结束点。
- **会议也能派任务**：讨论还没有结论就开始动手，正是会议要避免的；行动项回到主线后由主管处理。
- **只把纪要交回去，不保留原文链接**：纪要有损，事后追问“当时为什么否掉方案 B”会无据可查。
- **会上照常写记忆**：被否掉的想法会被记住。

## Consequences

- 纪要的质量决定了主线能不能接上讨论的结果，需要用真实模型验收。
- 主管的 `thread_read` / `thread_search` 加 `thread` 参数，有了跨线程读取的权限边界。
- 每次散会要多几次模型调用（生成纪要和校验），用量记在 `compactor` 名下。
- 设计见 `work/specs/notes-meetings-agent-chat`。
