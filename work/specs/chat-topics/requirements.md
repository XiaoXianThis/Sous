# 话题：把一条对话按议题整理

## 现状

- 主线是一条按时间排的消息流：用户消息、主管回复、任务汇报、【任务进展】叫醒、跟进全都交错在一起。议题一多，用户要自己把它们拼回来。
- 主管回合进行中发来的消息只能等这一轮结束，下一轮和其他未回复的消息合在一起答（`unanswered` 只看最新一条）。补充来晚了：任务可能已经按旧要求派出去；不相关的新话题也被混进同一次回复。
- 任务的进展都以消息的形式追加，噪音大；推送也一条一条地弹。
- 主管和子 agent 之间说了什么（派发的提示词、追加指令、agent 的进度、提问和回答、结果）分散在 Run 的事件里，界面上看不到完整的来回。

## 需求

- R1 话题：对话里的每条消息属于一个话题。在全局输入框发的消息开一个新话题；在话题里回复就继续那个话题。主管的回复、它派的任务、任务的汇报和叫醒、它对汇报的评论都落在同一个话题里。主管仍然只有一份上下文，能看到所有话题（不同话题之间可以互相参考）。
- R2 一轮只处理一个话题：主管一轮回答一个话题里还没回复的消息，别的话题各自一轮，按最早的未回复消息排队。
- R3 插话：主管回合进行中发来的消息，在下一次调用模型之前插进当前请求：
  - 发在当前话题里的，按补充处理；
  - 在全局输入框发的（自成一个新话题、只有这一条），让主管判断：是补充就用 `topic_attach` 并进当前话题并一起处理；不是就不管，它在这轮之后单独处理；
  - 别的已有话题里的消息不插。
- R4 有副作用的工具执行之前，如果来了 R3 的新消息，先不执行，让主管看完再决定。
- R5 连发：空闲时几秒内连发的几条消息合成一轮（短暂等待）。
- R6 并入可撤销：并入后用户可以把消息移回原来的话题，它会被单独处理。
- R7 话题的状态：进行中 / 要你处理 / 已结束；主管维护一两句“当前结论”，话题做完时主管关闭它并留一句总结。用户可以改标题、关闭和重新打开；关闭的话题有新消息（用户、汇报、叫醒）会自动重新打开。
- R8 界面：聊天区默认是话题视图——顶部“需要你处理”（待审批、等你验收、受阻的任务），下面按“要你处理 > 进行中 > 已结束（折叠）”排的话题卡片，有新动静的浮到上面，带未读标记。卡片收起时只显示标题、状态、当前结论和最新一句；展开是这个话题的完整对话、任务状态和话题内的输入框。保留“时间线”视图（原来的按时间排）。
- R9 汇报就地显示：任务汇报在话题里收成一行（任务、状态、一句摘要，可展开），任务状态在卡片的任务块里实时更新。
- R10 消息状态：用户消息在被主管处理前显示“排队中”，被看到（开始处理或插进当前回合）后显示“已看到”。
- R11 推送按话题合并：同一个话题的通知互相替换（同一个 tag），点开直接打开那个话题。
- R12 主管 ↔ 子 agent 的沟通：每个任务能看到它们之间说了什么——派发和返工的提示词、主管和用户的追加指令、agent 的进度、提问和回答、结果、验收结论、汇报。默认收起，展开才显示。在话题卡片的任务块和任务详情里都能看。
- R13 兼容：已有的消息没有话题，归在“更早的对话”里，照常显示；时间线视图不变。上下文缓存（决策 0020）不受影响：话题标记写在消息里，前缀仍然只往后追加。
