# 0014 服务器作为机器接入，部署和维护走运维任务

- Status: Accepted（“合并后自动部署”的触发方式被 0022 取代）
- Date: 2026-11-04

## Context

用户希望任意多台服务器也能像个人电脑一样接入，让 sous 把“写代码 → PR → 合并 → 部署 → 维护”跑通。服务器上没有 worktree 和 PR 的概念，要在真实目录里就地执行；而且生产机上出错的代价比开发机大得多。

## Decision

- 机器有角色：**开发机**（dev，默认）或**服务器**（server），写在机器本地的 `node.json`。配对时可以 `--role server`；Hub 可以把开发机改成服务器，**不能远程改回开发机**，只能在那台机器上改 `node.json`。
- 默认路由：代码任务和一般任务优先派到开发机，运维任务（`kind: ops`）优先派到服务器；没有这类机器能做时用别的机器，并告诉主管派到了哪里（0025 起，原来是“只派到”）。明确指定机器时不受角色限制。
- 运维任务在项目登记的部署目录里**就地执行**：不建 worktree、不交付 PR、不经过 reviewer 验收，以 agent 的总结作为汇报。提示里写明部署目录、部署命令和健康检查命令，要求按脚本执行；健康检查由 agent 在最后执行并写进总结，Node 不另外执行配置里的命令（和 0012 一致：Hub 不能让 Node 跑任意命令）。
- 服务器上的本地策略更严格，由 Node 执行，Hub 不能放宽：不能使用完全开放模式（降级为默认）；改文件、删除、启停服务（新增的 `service` 类：`systemctl`、`docker compose up/down/restart`、`pm2` 等）和不可逆操作一律交给用户，不经 AI 审批。
- 部署的触发：sous 永远不合并 PR（0009）。项目可以打开“合并后自动部署”：Hub 每 5 分钟（以及启动后 30 秒）请一台在线开发机用 `gh pr view` 查 sous 开出的 PR，已合并的就创建一个运维任务，每个 PR 只触发一次；任务完成后已经手动部署过的不再重复。也可以在项目页点“部署”或在对话里让 sous 部署。

## Alternatives

- Node 在 Run 结束后自己执行健康检查：结果更可靠，但等于 Hub 能让服务器执行一条配置里的命令。
- sous 合并 PR 后自动部署：违背 0009。
- 服务器也允许完全开放模式：生产机上风险太大。

## Consequences

- 项目多了部署目标（服务器、目录、部署命令、健康检查、是否合并后自动部署）。
- 这仍然是安全网，不是隔离（0010）：按命令文本识别 `service` 类，换个写法（比如写进脚本）就能绕过；真正的隔离仍在第二期。
