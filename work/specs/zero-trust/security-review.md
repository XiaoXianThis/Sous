## 1. 加密方式

| 用途 | 算法 | 实现 |
|---|---|---|
| 签名（名册、会话证书、许可、租约、快照清单、通道开启、发布） | ECDSA P-256 + SHA-256，签名格式 r‖s（64 字节），带上下文标签 `sous/v1/doc/<类型>` | Go 标准库；浏览器 WebCrypto（会话、身份签名私钥不可导出） |
| 密钥封装 | HPKE（RFC 9180），KEM = X-Wing（ML-KEM-768 + X25519 混合，抗量子），KDF = HKDF-SHA-256，AEAD = AES-256-GCM | Go 1.26 `crypto/hpke`；浏览器 `@noble/post-quantum` + 自写 HPKE 密钥调度，两边共用测试向量 |
| 通道（Node ↔ 大脑 ↔ 页面会话） | 每条单向通道一次 HPKE 封装，导出 32 字节密钥；之后每条消息 AES-256-GCM，nonce = 序号计数器，AAD = `通道 id ‖ 序号`；开启消息由发送方签名，绑定发送方、接收方、接收方 KEM 公钥 id | `trust/channel.go`、`web/src/trust/channel.ts` |
| 大脑状态（中继上的快照） | 域密钥（32 字节，按纪元轮换）用 HPKE 封装给用户身份和每台大脑；快照按 4 MB 分块 AES-256-GCM（随机 nonce，AAD = 快照序号 ‖ 块号），清单由租约持有者签名 | `trust/domain.go`、`brain/snapshot.go` |
| 身份私钥的保管 | WebAuthn PRF（`hmac-secret`）输出 → HKDF-SHA-256（随机盐）→ AES-256-GCM 包装身份私钥，密文存在中继上 | `web/src/trust/vault.ts` |
| 关键操作 | WebAuthn 断言，challenge = SHA-256(`sous/v1/critical` ‖ 指令字节)，验证方自己核对 rpIdHash、origin、UP+UV 标志、签名、一次性 | `trust/webauthn.go` |
| 配对 | 用户手动搬运的配对串：身份公钥指纹（32 字节）+ 128 位一次性秘密；双方消息 HMAC-SHA-256 | `trust/pairing.go` |
| 发布 | 离线 P-256 发布密钥签 `checksums.txt`，公钥编译进二进制 | `update/release.go` |

强度：P-256、X25519、AES-256 均 ≥128 位安全强度；X-Wing 的任一半成立即安全。没有任何密钥从口令派生。没有自创原语。

## 2. 安全的情况（代码已经保证，测试覆盖）

1. **中继是恶意的**：读不到聊天、任务、Run 输出、模型 Key（全部是端到端密文）；伪造不出任何一方的签名；重放旧消息会被通道序号拒绝，重放整条旧通道会被持久化的 `Seen` 表拒绝（10 分钟窗口 + 落盘）；重排、丢消息会被发现（链路直接断开重连）；拿出旧名册会被版本号拒绝；拿出旧租约会因过期或任期低被拒绝；把密文挪给别的接收者、别的用途会因 HPKE info / AAD 不符而解不开。
2. **配对时的中间人**：配对串不经过中继，中继既不知道 128 位秘密，也伪造不了身份指纹，替换任何一方的公钥都会配对失败。
3. **网络中间人 / TLS 被破**：安全不依赖 TLS，结论同 1。
4. **“现在截获、以后解密”**：通道和密钥封装用 X-Wing，量子计算机破了 X25519 也还有 ML-KEM-768。
5. **伪造关键操作**：打开终端、装/登录 agent、写 API Key、写配置、改角色或工作空间、安装更新、解冻、改自主范围、增删机器和 Passkey，都需要一次带 UV 的 WebAuthn 断言，由机器或大脑自己核对，签的就是这条指令（或许可）。页面、中继、大脑都伪造不了。
6. **更新被劫持**：CI 或 GitHub 被攻破也装不上未经离线密钥签名的版本；安装更新本身是关键操作。
7. **页面会话被偷走后的时效**：会话证书最长 24 小时（默认约为锁定时长的 2 倍），过期后每条消息都会被拒（`SenderOK` 逐条检查）。
8. **被踢出的机器**：名册版本单调，踢出时轮换域密钥，它读不到之后的快照；它发来的通道被拒绝。
9. **普通 Node 之间**：一台普通 Node 不能给其他机器下指令（机器只接受当前租约大脑的链路和用户会话的许可）。
10. **大脑在自主范围外的硬操作**：越权指令被机器拒绝，10 分钟内 3 次会让机器自我冻结；`open` 模式还受本机 `node.json` 否决。
11. **强行暴力破解**：没有低熵密钥；唯一低熵输入是设备 PIN，由安全芯片防重试。

## 3. 不安全或有条件的情况

按严重程度排列。前两条与 requirements 的承诺不一致，建议在发布 alpha 前修。

### 3.1 【高】一台普通 Node 被攻破，就能读全部聊天、替用户审批（违反 S5）

`brain/serve.go` 的 `MachineMessage` 允许任何名册里的机器调用 `/api/v1/device/*`，而这些接口对所有机器一视同仁：

- `GET /api/v1/device/threads`、`GET /api/v1/device/threads/{id}/messages`：列出并读取**所有**对话；
- `POST /api/v1/device/threads/{id}/messages`：以用户的名义往任意对话里发消息，可以借主管之手在自主范围内给其他机器派活；
- `GET /api/v1/device/approvals`、`POST /api/v1/device/approvals/{id}/decide`：查看并**批准**任意机器上的权限审批。

`nodehub.DeviceAuth` 只检查机器存在且没被吊销，没有按机器或角色过滤（`DeviceOf` 没有被任何处理函数使用）。所以 S5 的“读不到聊天记录”“无法冒充用户”在当前实现里不成立。`sous chat`、`sous note`、`sous mcp` 就是走这条路。

建议：默认关闭机器的设备接口，在 `node.json` 或名册里按机器显式开启（开启是关键操作）；审批只允许审批本机发起的那条；对话至少限制在本机创建的线程。

### 3.2 【中】关键操作的许可没有绑定内容

`node/guard.go` 核对 admin 许可时只比较字符串参数，并且有意跳过了 `content`、`value`、`base_sha256`；页面的许可也只写了 `op`、`agent`、`file`、`name`（`web/src/lib/api.ts`）。结果：

- `config.write`：用户刷 Face ID 批准“写 X 文件”，被攻破的大脑可以写入任意内容（例如给 agent 配置加 hook，变成任意命令执行）；
- `agents.set_env`：可以换成别的 Key 值；
- `node.set_role`、`node.set_workspaces`：角色和工作空间列表都不在许可里，可以把工作空间改成整个磁盘。

前提是大脑已被攻破，且用户正好在 5 分钟内批准了同类操作，许可只能用一次。但这让 S6 的“关键操作伪造不了”打了折扣。建议：许可里带上请求体的 SHA-256（和大脑侧的 `Intent.body_sha256` 一样），机器按完整参数核对。

### 3.3 【中，设计取舍】被攻破的大脑 ≈ 所有机器上的 auto 模式代码执行

这是 S6 的本意，但边界比字面宽：

- 大脑持有域密钥，能读全部数据（目前只有一个数据域，不能按项目排除大脑，design §17 已说明）；
- 自主范围只按机器、权限模式、`kind == "ops"`、`git.op == "merge"` 判断，而 `kind` 和 `git.op` 是大脑自己填的；设计里的 `repos` 白名单没有实现。被攻破的大脑可以把部署、合并写进普通 Run 的 prompt，在 auto 模式下让 agent 去做；
- `run.message`、`run.resume` 不受范围检查（只看暂停）。

因此：只把干净的个人电脑指定为大脑；服务器、部署目标不要当大脑，也不要和中继放在同一台。

### 3.4 【中，取决于托管】页面就是信任根

- 解锁时，身份签名私钥以 JWK 形式短暂出现在 JS 内存里，身份 KEM 私钥（X-Wing，noble 实现）一直是 JS 字节数组。页面一旦被换成恶意代码（Vercel 账号、域名、构建机被攻破，或出现 XSS），就能在下一次解锁时拿走身份私钥，读到所有数据并签发会话证书。
- 资源清单签名（design §9）没有实现，被篡改的页面不会被发现。
- 关键操作仍然要每次 Face ID，所以恶意页面不能“悄悄”做关键操作，但它可以把展示给用户的内容和实际签的内容做成不一样。

缓解：Vercel 开硬件 2FA、只从本机部署、严格 CSP（已有）。

### 3.5 【低】机器私钥是软件密钥

`~/.sous/trust/keys.json`（0600），没有 Secure Enclave / TPM。拿到这台机器的用户权限就能永久冒充它，直到被踢出。影响范围同 3.1。

### 3.6 【低】协议细节

- `trust.VerifyAssertion` 收到 `now` 但没有用：断言本身没有时效，时效靠被签内容里的 `iat`（许可、意图有检查；名册、自主范围靠版本号单调防重放）。目前没有可利用的路径，但函数注释和设计说的“不超过 5 分钟”不符。
- `AcceptRoster` 没有检查 `prev` 哈希链（design §3.4），只靠版本号单调。只有身份密钥能签名册，所以无法分叉，属于一致性缺口。
- 用过的断言 challenge、已用许可只存在内存里，进程重启后清空；由许可自身 5 分钟有效期和通道的持久化防重放兜底，目前无可利用路径。
- 中继能看到元数据：谁在线、什么时间、多少字节、配对房间。拒绝服务防不住。
- 首次设置是“谁先拿着 `sous-relay init` 令牌认领谁就是主人”，令牌泄露前要尽快认领。
- 迁移前留在旧 Hub 服务器上的明文数据和模型 Key 无法保证清除，建议轮换模型 Key（design §13 已说明）。

## 4. 结论

密码学选型和实现是扎实的：算法标准、上下文绑定完整、防重放和防回滚都落实了，测试覆盖了 design §12 的恶意中继攻击。**中继完全不可信的前提下是安全的。**

不满足承诺的是“一台普通 Node 被攻破只损失这一台”（3.1），以及关键操作许可不绑定内容（3.2）。建议修完这两条再发 `v0.3.0-alpha1`。
