# 参考 DeepSeek Super-agent

**适用场景**：设计或实现 sous 的事件模型、任务和执行、权限与审批、主动工作、失败恢复、提示词组织时；以及遇到“常驻 agent 该怎么处理 X”这类问题、拿不准方案时，先读这份文档，再去原型里找对应的思路。

## 它是什么

- 仓库：https://github.com/deepseek-ai/dsh-superagent-prototype （MIT 协议）
- 配套文章：《Super-agent 设计探索：迈向更自主的 Agent 系统》（DeepSeek Harness 团队，2026-10-31）
- 形态：基于 DeepSeek Harness 的插件，TypeScript 编写。它是一个面向**单个 GitHub 仓库、服务整个团队**的主动式编程 agent：监听 GitHub 和飞书，接到请求后开工单，在独立的会话和目录里干活，最后在原对话里回复，比如提一个 PR。
- 定位：**研究原型**，官方说明了不能直接用于生产。我们借鉴的是思路，不照搬实现；如果要复制代码片段，需要保留 MIT 署名。

## 概念对照

| Super-agent | sous | 说明 |
|---|---|---|
| Source + Trigger | Channel / Trigger + Event | 它是外部事件流；我们统一记成事件 |
| Thread | Thread | 同一线程里同一时刻只做一次判断 |
| Eval（准入 + 研判） | 主管循环的一轮 | 它把“要不要开工”单独拆成 Eval；我们并在主管循环里 |
| Mandate | 任务的权限快照 | 记录这项工作凭什么能做、能做到多大范围 |
| Ticket | Task | 工单有自己的状态，不跟随执行端的状态 |
| Assignment | Run | 一个工单在不同时间可以有多次派工 |
| Executor Session + 目录 | Node 上的 Worker + worktree | 它只有一台机器、一种 agent；我们有多台机器、多种 agent |
| Report（progress / waiting / ready / blocked / failed / dropped） | `run.update` / `run.ended` | 建议直接沿用这组汇报类型 |
| Attention | Approval / 向用户提问 | 结构化的单个问题，等待人来回答 |
| Effects + Outbox | 事件投影之后的副作用队列 | 先落库，提交之后再执行 |
| 面板只显示需要人处理的事 | PWA 首页 | 状态健康时不占任何地方 |

## 值得借鉴的思路

**原则**
1. **注意力是最贵的资源。** 只在两种情况下说话：需要用户行动，或者有用户用得上的结果。接到任务确认一次，干活期间保持安静，有结果、需要决定、做不下去时再开口。
2. **一次只问一个具体问题**，并且用结构化的形式问，不要把问题埋在长篇报告里。
3. **按影响决定停在哪里，而不是按工作量。** 局部改动做到能评审的程度为止；需要做设计决策的，停下来提一个明确的问题。
4. **如实汇报。** 草稿标成未完成，失败就报失败，不为了少问一句而绕过限制。
5. **概念少，配置少。** 业务需求要么变成已有概念的一个属性，要么写进提示词。几乎所有人都用同一个值的，就用默认值，不做成配置项。

**架构**
6. **只有一个写入者。** 它的 Engine 是领域数据唯一的写入方；每条命令在一个事务里完成，外部副作用在事务内入队、提交后再执行（事务性 outbox）。对应到 sous：只有一个组件负责追加事件和更新视图，推送通知、下发任务给 Node 都通过副作用队列执行。
7. **副作用的重试策略**：第一次失败后 2 秒重试，之后间隔翻倍，最长 1 分钟；同一项连续失败 3 次才作为系统问题暴露出来；有顺序要求的消息，前一条失败会挡住后面的。
8. **线程内串行，并且合并批次。** 判断进行期间新到的事件，合并进下一批一起处理，而不是逐条触发。
9. **工单的阶段是推导出来的**：按优先级从上到下匹配状态表，第一条命中的就是当前阶段，比如“等人回答”“等人评审”“受阻”“排队”“执行中”。其中“需要人处理”的那几类阶段，正好就是 PWA 首页要展示的内容。
10. **追加消息通过订阅扇出到任务。** 任务开始之后，线程里的后续消息直接作为上下文送给正在执行的任务，不需要重新判断要不要开工。

**主动工作**
11. **接单模式分三档：off / observe / auto**，默认 observe。主动发现的工作，在 observe 模式下只记录“我本来会这么做”；用户看过这些记录、觉得可靠之后，再切到 auto。sous 的定时触发和主动跟进可以照这个思路做（目前还没写进需求，见 spec）。
12. **规则变化时不取消正在进行的工作**，而是把变化作为一条输入送给受影响的任务，由它自己调整。

**执行与恢复**
13. **执行端在前台跑的命令超过 5 秒，就转到后台**，这样 agent 能在下一步收到新消息，不会被长命令卡住；一轮结束后，后台任务最多再运行 30 分钟。
14. **临时性故障**（HTTP 408、429、5xx，连接被拒绝、被重置或超时）自动重试 3 次，间隔逐渐拉长；其他失败不自动重试，等人处理。
15. **重启恢复**：重启时正在运行的派工，以“宿主已重启”结束；新的派工会带上一段恢复说明，要求执行端**先检查目录、git 历史和远端状态，再决定要不要重复任何对外操作**。按工单从旧到新的顺序恢复。
16. **消息的投递需要精确记录。** 记下哪些消息已经进入执行端的历史，重试或重启时只补发没被读取的消息，避免重复投递。

**提示词**
17. **提示词分层组装**：共享指令 → 角色 → 用户自定义部分 → 工作说明 → 环境 → 策略。经常变化的部分放在最后，这样前面的部分能命中提示词缓存。
18. **覆盖默认提示词时记录它基于哪个版本**，默认版本升级后可以展示差异，由用户决定保留自己的还是用新的。
19. **安全边界由代码保证，不交给提示词。** 消息、评论、引用的文档只是判断的输入，不能改变权限；提示词怎么改，都不影响准入、授权和工具检查。

## 我们和它的不同

| 方面 | Super-agent | sous |
|---|---|---|
| 服务对象 | 一个团队，在一个仓库上 | 一个人，跨多个项目 |
| 入口 | GitHub、飞书 | PWA、命令行（以后会加更多） |
| 执行端 | 同一台机器上的 DeepSeek Harness 会话 | 多台机器上的 5 种编程 agent（通过 ACP 接入） |
| 执行权限 | 以操作者的系统用户身份运行命令，不经审批 | 三档权限模式加审批 |
| 部署 | Harness 插件，单进程 | Hub 放在服务器，Node 放在各台电脑 |

## 原型自己承认的不足（我们要避开）

- 不会删除任何旧记录，表会无限增长。sous 要从一开始就规划数据保留和归档策略。
- 哪些字段可信、哪些不可信（比如消息正文和引用内容），在原型里还是一个开放问题。sous 的原则是：**来自外部的所有内容都只是数据，不是指令。**
