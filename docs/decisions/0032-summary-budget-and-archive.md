# 0032 摘要的预算：过期待办丢弃，旧决定和偏好归档到长期记忆

- Status: Accepted
- Date: 2026-11-12

## Context

决策 [0020](0020-long-thread-context.md) 规定，“已做的决定”和“待办和承诺”里的条目只能移到“已完成或作废”，不能消失。主线是一条不会结束的对话：决定大多一直成立，不会“完成”；没人跟进的待办也一直挂着。这两栏只增不减，“用户的偏好和纠正”也不压缩。提示词里的“3000 字以内”和“前三栏不压缩”互相矛盾，代码层面也没有上限。时间一长，旧条目会稀释主管的注意力，最终挤占上下文。

## Decision

每次整理写完摘要后，由代码（`supervisor/archive.go` 的 `tidy`）再做两件事：

- **过期待办直接丢弃**：一条待办引用的最新消息早于 14 天（`StaleTodoAge`），就移到“已完成或作废”，并注明“过期丢弃”；下一次整理时这一栏会被清掉。没有来源编号的待办保留。不问用户：用户的习惯就是丢弃过期待办。
- **超预算就归档**：摘要正文（不含工具回执存档，它另有 6000 字的上限）估算超过窗口的 8%（`SummaryBudgetRatio`）时，从最旧的“已做的决定”和“用户的偏好和纠正”开始，逐条写进长期记忆（决定记为 `note`，偏好记为 `profile`；已有相同记忆就不重复写），再从摘要里移出，直到降到窗口的 5%（`SummaryTargetRatio`）。“其他背景”里保留一行“较早的决定和偏好已归档到长期记忆（共 N 条）”。模型漏掉这一行时，由代码按旧摘要补回。会议线程不归档。

写记忆失败的条目留在摘要里，不会丢。

## Alternatives

- 按时间丢弃旧决定：决定通常一直有效，丢了会悄悄违背已经定下的事。
- 过期待办先问用户：用户的习惯是直接丢弃，问一次反而打扰。
- 只靠提示词控制长度：模型做不到，而且和“前三栏不压缩”冲突。

## Consequences

- 摘要正文大致维持在窗口的 5% 到 8% 之间。窗口为 128K 时约 6K 到 10K token，为 200K 时约 10K 到 16K token。
- 归档的决定不再每轮出现在上下文里，主管需要时用 `memory_search` 查，原文用 `thread_search` 和 `thread_read`。
- 偏好进入画像记忆后，每段的段首快照最多带 30 条（`ProfileLimit`），更多的要靠检索。
